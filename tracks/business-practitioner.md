# 현업 실무자 협업 안내

## 대상

고객지원, 영업, 마케팅, 물류, 제조, 재무, 인사, 법무 등 업무를 가장 잘 알고 결과를 사용하거나 승인하는 담당자를 위한 협업 안내다. 개발 경험을 전제하지 않는다.

## 목표

“AI로 무엇을 만들까”보다 “어떤 업무를 왜 바꾸고, 무엇을 담당자 책임으로 남길까”를 설명한다. 구현자에게 요구사항을 전달하는 데 그치지 않고 검수·예외·현업 정착·기존 절차 종료까지 책임진다.

## 1. 실제 업무를 보이게 만든다

알아야 할 것:

- 업무의 시작 신호, 입력, 담당자, 판단, 출력, 대기, 예외
- 문서에 적힌 절차와 실제 처리 방식의 차이
- 자주 발생하는 사례와 드물지만 영향이 큰 사례

해볼 것:

- 최근 실제 사례 5~20건을 골라 흐름과 소요 시간을 기록한다.
- “보통은 이렇게 한다” 대신 사례별 차이를 표시한다.
- 일이 완료됐다고 판단하는 사람과 기준을 적는다.

결과물:

- [업무 발굴 카드](../toolkit/workflow-discovery-card.md)
- 현재 업무 흐름
- 예외 목록과 기준선

## 2. 목표 흐름과 담당자 판단을 정한다

각 단계를 제거, 통합, 표준화, AI 보조, 담당자 승인, 제한된 자동 실행으로 다시 분류한다. 판단 근거를 설명할 수 없는 단계는 곧바로 자동 실행하지 않는다.

확인할 질문:

- 이 단계는 왜 존재하는가?
- 규정이나 계약 때문에 필요한가, 관행 때문에 남았는가?
- 실수했을 때 고객·금전·안전·권리에 어떤 영향이 있는가?
- 사람이 최종 책임져야 할 판단은 무엇인가?

결과물:

- 목표 업무 흐름
- 담당자 판단과 승인 기준
- 범위와 비목표

## 3. 데이터와 용어를 정리한다

업무에서 최신 사실을 확인하는 위치와 데이터 소유자를 적는다. 팀마다 같은 말을 다른 뜻으로 쓰면 모델보다 용어부터 맞춘다.

해볼 것:

- 원본 시스템·공식 문서·개인 파일을 구분한다.
- 필수 입력과 자주 빠지는 값을 적는다.
- 핵심 용어와 지표를 실제 예시로 정의한다.
- 출처가 없거나 충돌하는 경우의 처리 방식을 정한다.

결과물:

- 원본과 소유자 지도
- 업무 용어집
- 누락·충돌 사례

## 4. 검수 기준을 만든다

좋은 결과를 느낌으로 고르지 않는다. 정상, 경계, 금지 사례를 모으고 결과를 `통과`, `수정 후 통과`, `거절`, `담당자 판단 필요`로 판정한다.

검수 기준에는 다음을 넣는다.

- 사실이 맞고 출처를 확인할 수 있는가?
- 업무 형식과 필수 항목을 지켰는가?
- 개인정보·기밀·차별·과장 위험이 없는가?
- 다음 행동을 해도 되는가, 제안만 해야 하는가?

결과물:

- 업무 사례 기반 평가 세트
- 판정 기준과 판정자
- 수정 이유 기록

## 5. 사용자 검수와 공식 절차를 바꾼다

구현자 설명 없이 실제 사용자가 업무를 수행하게 한다. 사용하지 않는 이유를 교육 부족으로 단정하지 않고 접근성, 신뢰, 입력 부담, 예외 처리, 기존 KPI와의 충돌로 나눈다.

해볼 것:

- 대표 사용자와 사용자 검수를 진행한다.
- 새 절차, 도움 요청, 장애 시 수동 처리를 SOP에 반영한다.
- 이중 운영 기간과 기존 절차 종료 조건을 정한다.
- 로그인 수가 아니라 완료 시간, 수정 부담, 예외, 지원 요청을 본다.

결과물:

- 사용자 검수 기록
- 새 SOP와 교육 자료
- 기존 절차 유지·종료 결정
- 실제 사용과 업무 결과 지표

## 개발자와 합의할 경계

- 모델이 제안하는 단계와 시스템이 실행하는 단계
- 읽기 권한과 쓰기 권한
- 평가 세트의 사용 범위와 변경 승인
- 오류가 났을 때 자동 재시도, 담당자 인계, 즉시 중단의 구분
- 로그에 남길 정보와 남기지 않을 개인정보

## 자주 발생하는 실패

- 가장 눈에 띄는 반복 작업을 기준선 없이 선택한다.
- 현재 절차의 불필요한 단계를 그대로 자동화한다.
- “사람이 검토한다”고만 쓰고 기준과 권한을 정하지 않는다.
- 좋은 예시만 검수하고 예외·금지 사례를 빼놓는다.
- 새 도구 교육만 끝내고 현업 정착이 완료됐다고 판단한다.
- 기존 절차를 종료하지 않아 일이 두 배가 된다.
