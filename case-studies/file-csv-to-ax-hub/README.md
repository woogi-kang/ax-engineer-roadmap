| 구분 | 쓰기 영향 | 자율성 | P 단계 |

> 공개 사례 연결: K10·G04·G05의 기록 통합, 현장별 지식 차이, 제품·버전 제약을 [공개 사례 적용 맵](../../research/public-case-application-map.md)에서 데이터 계약 질문으로 연결했다.

여기서 **AX Hub**는 여러 파일과 메시지의 원본 연결, 담당자, 검토 상태를 한곳에서 확인하는 얇은 업무 조정 계층을 뜻한다. 기존 원본 시스템을 대체하는 새 전사 데이터베이스가 아니다.

개인 AI 도구의 산출물, 여러 폴더에 흩어진 CSV, 회의에서 나온 막힘·승인 신호를 구조화된 업무 기록으로 모으고 Slack 요약 초안을 만드는 **학습용 AX 업무 전환 시뮬레이션**이다. 특정 회사에서 실제로 도입했거나 시간·비용·품질이 개선됐다는 사례가 아니다.

## 현재 실행물과 근거

현재 공개한 근거는 시뮬레이션 설계 문서다. `ready`는 이 설계로 공개·합성 데이터 시뮬레이션을 시작할 준비가 됐다는 뜻이며, 운영 환경에서 효과가 확인됐다는 뜻은 아니다.

향후 시뮬레이션을 실행해 공개할 수 있는 범위는 합성 CSV, 식별 정보를 제거한 예시 산출물, 스키마, 평가 결과, 장애·복구 기록으로 제한한다. 실제 조직의 문서, 개인 프롬프트, 고객·직원 정보, 접근 토큰은 사용하지 않는다.

## 2. 문제와 사용자

### 문제

개인이 AI로 만든 조사·요약·아이디어는 문서나 채팅 기록으로 남고, 실제 업무 상태는 서로 다른 CSV에 나뉜다. 회의에서 결정한 담당자와 마감일, “막힘”, “승인 대기”, “승인” 같은 신호는 회의록이나 메시지에만 남기도 한다.

이 상태에서는 다음 질문에 답하려고 다시 파일을 열고 사람에게 확인해야 한다.

- 같은 업무가 어느 파일에도 중복돼 있는가?
- 최신 상태와 담당자는 무엇인가?
- 막힌 이유와 다음 결정권자는 누구인가?
- 승인은 실제로 누가 언제 했는가?
- Slack에 공유할 내용이 원본과 맞는가?

### 사용자와 책임

| 사용자 | 필요한 결과 | 맡는 책임 |
|---|---|---|
| 업무 담당자 | 본인이 맡은 일, 막힘, 다음 행동 | 원본 상태와 담당자 확인 |
| 팀 리드·승인자 | 승인 대기 항목과 판단 근거 | 승인·보류·기각을 직접 기록 |
| 운영 담당자 | 누락·중복·오류가 보이는 목록 | 검토 큐 처리와 수동 복구 |
| AX 엔지니어 | 출처를 추적할 수 있는 구조와 실행 기록 | 매핑, 권한, 평가, 장애 대응 |

현재 기준선은 처리 시간을 추정한 숫자가 아니라 다음과 같은 업무 상태로 기록한다.

- 원본 파일과 개인 산출물의 위치를 한 번에 찾을 수 없다.
- 상태·담당자·마감일의 필드 이름과 허용값이 파일마다 다르다.
- 회의에서 나온 막힘과 승인 여부를 CSV 행에 다시 옮기는 규칙이 없다.
- Slack 요약과 원본 사이를 역추적하는 식별자가 없다.
- 수정·재실행·중복 처리 기록이 남지 않는다.

잘못 합치면 오래된 상태가 최신 값처럼 보이거나, 단순한 논의를 승인으로 오해하거나, 제한된 정보가 더 넓은 Slack 채널에 노출될 수 있다.

## 3. 현재 업무 흐름

```text
개인이 AI로 조사·요약
→ 각자 문서나 대화 기록에 보관
→ 여러 CSV에서 업무 상태를 따로 갱신
→ 회의에서 막힘·담당자·승인을 논의
→ 누군가 파일과 회의록을 다시 대조
→ Slack 요약을 수동 작성
→ 원본 변경 뒤 요약이 오래돼도 별도 표시가 없음
```

병목은 “파일을 한곳에 모으지 못했다”는 데만 있지 않다. 어떤 원본을 기준으로 삼을지, 서로 충돌하는 값을 누가 확정할지, 승인을 어떤 사건으로 남길지가 정해지지 않은 것이 더 큰 문제다.

## 4. 목표 흐름과 기준 정보의 역할

### 목표 흐름

```text
허용된 개인 AI 산출물·CSV·회의 신호 등록
→ 원본 해시·수정 시각·소유자 기록
→ 필드 매핑과 형식 검사
→ 중복·충돌·민감 정보 의심 항목 격리
→ AX Hub 구조화 DB v0에 검토 초안 생성
→ 담당자가 원본과 대조해 병합·수정·기각
→ 막힘과 승인 상태를 명시적으로 확정
→ 검토 완료 레코드만 Slack 요약 초안에 포함
→ 사람이 마지막으로 확인해 게시
→ 게시본과 Hub 레코드 식별자를 함께 기록
```

시스템은 승인 상태를 문맥에서 추측하지 않는다. 회의록에 “좋아 보인다”가 있어도 승인자가 명시된 승인 동작을 하지 않았다면 `approval_state`는 바뀌지 않는다.

### 시스템별 기준 정보 역할

| 시스템·자료 | 기준 정보 역할 | 이 흐름에서 하는 일 | 하지 않는 일 |
|---|---|---|---|
| 개인 AI 산출물 | 아이디어·분석 초안의 원본 | 출처와 작성 시각을 붙여 후보 자료로 등록 | 사실 또는 최종 결정으로 자동 승격하지 않음 |
| 분산 CSV | 각 업무 소유자가 관리하던 원본 기록 | 읽기 전용 스냅샷으로 가져와 필드를 매핑 | 원본 파일을 덮어쓰거나 의미가 다른 열을 임의 병합하지 않음 |
| 회의록·막힘 신호 | 결정 맥락과 예외의 출처 | 원문 위치와 시각을 보존해 검토 후보를 만듦 | 막힘의 원인, 담당자, 승인 여부를 추론해 확정하지 않음 |
| 명시적 승인 사건 | 승인 여부의 유일한 기준 | 승인자, 시각, 대상 버전을 기록 | 모델 응답이나 이모지만으로 승인을 만들지 않음 |
| Notion 스타일 AX Hub / 구조화 DB v0 | 검토를 마친 통합 상태의 기준 | 업무, 출처, 담당자, 막힘, 승인, 검토 상태를 연결 | 모든 원본 파일을 폐기하거나 원본 내용 전체를 복제하지 않음 |
| Slack | 알림과 요약을 읽는 채널 | 검토된 레코드로 요약 초안을 보여 줌 | 승인·업무 상태·장기 기록의 기준이 되지 않음 |

AX Hub는 기존 원본의 소유권을 빼앗는 새 전사 데이터베이스가 아니다. v0에서는 “어떤 레코드가 어느 원본과 연결되고, 누가 검토했는가”를 관리하는 얇은 조정 계층으로 둔다.

### 구조화 DB v0의 최소 필드

| 필드 | 의미 | 작성 규칙 |
|---|---|---|
| `record_id` | Hub 내부의 안정적인 식별자 | 재실행해도 같은 원본·버전이면 바뀌지 않음 |
| `record_type` | 조사, 업무, 결정, 막힘 등 레코드 종류 | 허용값 밖이면 격리 |
| `title` | 사람이 읽을 짧은 제목 | AI 생성 시 검토 전까지 초안 표시 |
| `source_type` | AI 산출물, CSV, 회의록 등 출처 종류 | 필수 |
| `source_ref` | 원본을 다시 찾을 수 있는 위치 또는 식별자 | 비밀값과 개인 대화 전문은 넣지 않음 |
| `source_hash` | 가져온 원본 버전의 해시 | 원본 변경 감지에 사용 |
| `source_updated_at` | 원본이 마지막으로 바뀐 시각 | 시간대를 함께 기록 |
| `owner` | 업무 상태를 확인할 사람 | 비어 있으면 `needs_review` |
| `status` | 업무 진행 상태 | 허용된 상태 전이만 적용 |
| `blocker` | 막힘 내용과 해소 조건 | 출처 없이 생성하지 않음 |
| `approval_state` | `not_requested`, `requested`, `approved`, `rejected` | 사람의 명시적 사건만 `approved`로 변경 |
| `approved_by`, `approved_at` | 승인자와 승인 시각 | 승인 상태일 때 둘 다 필수 |
| `review_state` | `needs_review`, `reviewed`, `quarantined` | Slack 초안에는 `reviewed`만 사용 |
| `schema_version` | 매핑·필드 규칙 버전 | 가져오기 실행마다 기록 |
| `run_id` | 한 번의 수집·변환 실행 식별자 | 로그·복구·재실행을 연결 |

## 5. 범위, 제외 목표, 중단 조건

### 포함 범위

- 합성하거나 공개 가능한 개인 AI 산출물과 CSV의 출처 목록 작성
- CSV별 필드 매핑, 누락, 허용값, 최신성 규칙 정의
- 회의록에서 막힘·승인 **후보**를 찾되 사람이 확정하는 검토 큐
- 원본 버전과 연결된 구조화 DB v0
- 검토된 항목만 사용하는 Slack 요약 초안
- 실행 식별자, 변경 기록, 격리, 재실행, 수동 복구 절차
- 두 번째 워크플로우와 비교할 재사용 후보 기록

### 이번 범위에서 제외한 목표

- 실제 회사 자료를 한곳으로 이전하는 작업
- 원본 CSV를 자동 수정하거나 삭제하는 양방향 동기화
- AI가 담당자, 우선순위, 마감일, 승인 여부를 최종 결정하는 기능
- Slack 요약의 무검토 자동 게시
- 개인·고객·직원의 성과 평가
- 모든 문서와 대화 전문을 저장하는 검색 시스템
- 도구 도입만으로 시간·비용·품질이 개선됐다는 주장
- 제한된 운영 파일럿인 P4

### 중단 조건

- 원본 소유자와 공개 범위를 확인할 수 없다.
- 민감 정보 의심 항목을 격리하지 못한다.
- 서로 다른 CSV 값이 충돌하는데 우선순위를 사람이 결정할 수 없다.
- 승인되지 않은 항목이 승인 상태나 Slack 게시본에 들어간다.
- 같은 입력을 재실행했을 때 중복 레코드가 생긴다.
- 부분 실패 뒤 어느 항목이 반영됐는지 확인하거나 되돌릴 수 없다.
- 검토 큐가 쌓여도 담당자와 처리 기한을 정할 수 없다.

## 6. 구현·검증 단계와 P1–P5 연결

이 표는 완료 실적이 아니라 시뮬레이션에서 따를 구현 순서와 통과 기준이다.

| 프로젝트 | 이 사례에서 할 일 | 확인할 결과 | 다음 단계 조건 |
|---|---|---|---|
| P1 안전한 보조 도구 | 합성 파일을 읽어 필드 매핑, 누락, 중복, 상태 후보를 제안한다. 외부 시스템에는 쓰지 않는다. | 출처 목록, 스키마 v0, 평가 세트, 격리 결과 | 모든 출력이 원본 버전으로 역추적되고 모르는 값은 비워 둔다. |
| P2 담당자 승인 워크플로우 | 병합·상태·막힘·승인 후보를 사람이 수정·승인·기각한다. | 변경 전후, 검토자, 결정 이유, 승인 사건 | 모델이나 회의 표현만으로 승인 상태가 바뀌지 않는다. |
| P3 샌드박스 통합 | 검토된 가져오기 묶음을 격리된 구조화 DB v0에 운영자가 적용하고 Slack 요약 미리보기를 만든다. | 권한표, 중복 방지, 부분 실패, 롤백, 미리보기 | 흐름의 쓰기 영향은 초안에 머물고 원본과 Slack을 자동 변경하지 않는다. |
| P4 제한된 운영 | 이번 사례에서는 수행하지 않는다. | 해당 없음 | 실제 사용자, 기준선, 데이터 정책, 운영 책임자가 마련된 뒤 별도로 승인한다. |
| P5 두 번째 업무 재사용 | [Slack 회의 실행 항목 사례](../slack-meeting-actions/README.md)와 출처·검토·승인·실행 기록을 비교한다. | 재사용·수정·폐기 표, 버전 결정 | CSV 매핑 같은 업무별 규칙과 공통 실행 규칙을 분리한다. |

## 7. 평가와 실패 주입

### 평가 질문

- 모든 Hub 레코드를 원본 파일과 가져온 버전까지 추적할 수 있는가?
- 필드가 없거나 뜻이 충돌할 때 값을 만들지 않고 검토 큐로 보내는가?
- 승인 상태는 승인자·시각·대상 버전과 함께 남는가?
- 같은 입력과 `run_id`를 재실행해도 레코드와 요약 항목이 중복되지 않는가?
- Slack 초안의 각 항목이 검토 완료 Hub 레코드와 연결되는가?
- 운영자가 AI 설명 없이 로그와 원본을 보고 오류를 복구할 수 있는가?
- 사람이 어떤 필드를 얼마나 자주 고쳤는지 측정할 수 있는가?

통과 기준에는 최소한 다음 불변 조건을 둔다.

- 출처 없는 승인 0건
- 승인되지 않은 항목의 게시 0건
- 재실행으로 생긴 중복 부작용 0건
- 조용히 덮어쓴 충돌 0건
- 모든 격리·부분 실패의 `run_id`와 수동 처리 상태 기록

필드 정확도, 검토 시간, 수정 부담의 목표치는 실제 기준선을 확인하기 전에 임의로 정하지 않는다. 시뮬레이션 결과를 보고 업무 책임자와 다음 실험의 허용 기준을 정한다.

### 실패 주입 표

| 주입할 실패 | 기대 동작 | 남길 확인 자료 |
|---|---|---|
| CSV 인코딩·구분자·열 이름 변경 | 전체를 성공 처리하지 않고 해당 파일을 격리한다. | 오류 위치, 스키마 버전, 재처리 결과 |
| 같은 업무가 여러 CSV에 있고 상태가 다름 | 최신값을 임의 선택하지 않고 충돌 묶음을 만든다. | 후보 원본, 선택한 값, 결정자와 이유 |
| 원본 AI 산출물이 가져온 뒤 수정됨 | 해시 차이를 표시하고 이전 검토를 자동 승계하지 않는다. | 이전·현재 버전, 재검토 상태 |
| 회의록에 “승인 같음”처럼 모호한 표현이 있음 | 승인 후보로도 확정하지 않고 `requested` 또는 검토 필요로 남긴다. | 원문 위치, 검토 결과 |
| 담당자·마감일·시간대 누락 | 값을 추측하지 않고 누락 필드를 표시한다. | 누락률, 수정 유형 |
| 비밀값·개인정보처럼 보이는 문자열 포함 | Slack 초안과 일반 검토 화면에서 제외하고 제한 큐로 보낸다. | 탐지 규칙, 접근 기록, 폐기 여부 |
| 가져오기 도중 일부 레코드만 반영됨 | 반영·미반영 목록을 나누고 같은 실행 키로 안전하게 재개한다. | 커밋 지점, 재실행 결과, 중복 검사 |
| Slack 초안 생성 또는 게시 단계 실패 | Hub 상태를 성공으로 바꾸지 않고 초안 재생성 또는 수동 게시로 전환한다. | 실패 상태, 재시도 횟수, 수동 처리 |

정상 사례만 모은 평가 세트는 사용하지 않는다. 정상, 경계, 실패, 권한 거부 사례를 나누고 원본·기대 상태·실제 결과·사람의 수정 내용을 함께 보관한다.

## 8. 운영과 인수인계

### 역할

| 역할 | 운영 책임 |
|---|---|
| 업무 책임자 | 상태·승인 정의, 검토 처리 기한, 계속·중단 결정 |
| 원본 소유자 | 파일 의미, 열 매핑, 최신성, 보존 기간 확인 |
| 검토 운영자 | 격리·충돌 큐 처리, Slack 초안 최종 확인 |
| AX 엔지니어 | 가져오기, 상태 전이, 권한, 로그, 평가, 복구 유지 |
| 보안·개인정보 담당자 | 허용 자료, 마스킹, 접근, 보존·폐기 규칙 검토 |

### 운영 기록

한 번의 연습 실행마다 다음을 남긴다.

- `run_id`, 시작·종료 시각, 스키마·매핑 버전
- 읽은 원본 수, 생성 후보 수, 검토·격리·기각 수
- 중복·충돌·민감 정보 의심 수와 처리 상태
- 사람이 수정한 필드와 수정 이유
- Slack 초안 버전, 검토자, 게시 여부, 연결된 `record_id`
- 오류, 재시도, 수동 전환, 복구 결과

알림은 “성공” 한 줄로 끝내지 않는다. 일부 파일만 처리됐거나 검토 대기가 남았다면 부분 성공으로 표시하고 다음 담당자를 적는다.

### 인수인계 확인

- 비개발 운영자가 새 CSV 매핑을 추가하지 않고도 기존 매핑의 오류를 찾을 수 있는가?
- 원본 파일 하나를 제외하거나 다시 가져오는 절차가 문서화됐는가?
- 승인 사건을 정정할 때 이전 기록을 지우지 않고 새 사건으로 남기는가?
- Slack 게시 없이 Hub만 운영하거나, 자동 흐름을 멈추고 기존 수동 요약으로 돌아갈 수 있는가?
- 구현자 없이 대표 실패 세 가지를 진단하고 처리할 수 있는가?

## 9. 결과물

시뮬레이션을 실행하면 다음 결과물을 같은 `run_id`로 묶어 공개할 수 있어야 한다.

- 허용 자료와 제외 자료를 나눈 원본 목록
- 합성 AI 산출물·CSV·회의 신호 예제
- CSV별 필드 매핑과 구조화 DB v0 스키마
- 상태 전이, 승인, 검토, 격리 규칙
- 출처·버전·변경 기록
- 정상·경계·실패 평가 세트와 실행 결과
- Hub 목록·상세·검토 큐 화면 또는 동등한 산출물
- Slack 요약 초안과 원본 연결 예시
- 권한표, 운영 절차, 장애·복구 기록
- 사용자 검수와 재사용 결정문

## 10. 현재 결과와 한계

### 현재 결과

현재 공개할 수 있는 결과는 구현 전 설계다. 시스템별 기준 정보의 역할, 구조화 DB v0의 최소 필드, P1–P5 연결, 실패 주입과 운영 인수인계 조건을 검토 가능한 형태로 정했다. 평가 실행 결과나 조직 성과는 아직 없다.

### 한계

- 실제 회사의 파일 구조, 승인 절차, 데이터 분포를 대표하지 않는다.
- “Notion 스타일”은 관계형 보기와 검토 화면을 설명하는 표현이며 특정 제품 도입 효과를 뜻하지 않는다.
- CSV 열의 의미와 최신성은 원본 소유자의 설명 없이는 완전히 복원할 수 없다.
- 개인 AI 산출물은 사실과 아이디어가 섞일 수 있어 원본 자료와 별도 검토가 필요하다.
- 수동 검토의 처리량과 피로도는 시뮬레이션에서 측정한 뒤 판단해야 한다.
- 이 설계는 실제 Slack 게시, 운영 API, 개인정보 처리, 조직 권한을 검증하지 않았다.

### 주장하지 않는 것

- 실제 조직이 이 Hub를 사용한다는 주장
- 처리 시간, 비용, 품질, 협업 만족도가 개선됐다는 주장
- 분산 파일을 모두 통합하거나 원본 시스템을 대체했다는 주장
- AI가 승인이나 업무 우선순위를 정확히 판단한다는 주장

## 11. 재사용과 다음 결정

| 구분 | 결정 후보 |
|---|---|
| 그대로 재사용 | `run_id`, 출처·버전 필드, 검토 상태, 명시적 승인 사건, 중복 방지, 평가 결과 형식 |
| 수정해 재사용 | Slack 요약 형식, 담당자·상태 값, 검토 큐의 우선순위 |
| 업무별로 유지 | CSV 열 매핑, 파일 소유권, 회의 용어, 보존 기간 |
| 공통화하지 않음 | Notion 스타일 화면, 특정 폴더 구조, 모든 팀에 같은 상태값을 강제하는 규칙 |

다음 단계는 **P1–P3 합성 데이터 시뮬레이션**이다. 여기서 출처 추적, 승인 불변 조건, 중복 방지, 복구, 수동 검토 부담을 확인한다. P5에서는 다른 입력 구조를 가진 Slack 회의 사례에 실제로 재사용한 항목만 공통 실행 규칙 후보로 남긴다.

P4 운영 파일럿으로 넘어가려면 실제 업무 책임자가 기준선과 허용 자료를 정하고, 운영자가 검토 큐와 장애를 처리할 수 있으며, 보안·개인정보 담당자가 접근·보존 규칙을 승인해야 한다. 하나라도 충족하지 못하면 기존 수동 절차를 유지하거나 범위를 줄이거나 실험을 중단한다.
