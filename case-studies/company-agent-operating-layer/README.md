# 사례: 회사 에이전트 운영 계층

## 사례 성격

이 문서는 실제 회사에 배포한 전사 에이전트나 운영 성과가 아니다. 두 개의 서로 다른 업무에서 공통 실행 규칙을 재사용했다고 가정하고, 그다음 조직 수준에서 무엇을 공통화할지 검토하는 **학습·참고용 조직 캡스톤 시뮬레이션 설계**다.

이 사례에서 “회사 에이전트”는 모든 데이터와 권한을 가진 하나의 에이전트를 뜻하지 않는다. Slack·Microsoft Teams 진입점과 공통 운영 규칙은 공유할 수 있지만, 업무마다 신뢰 경계, 자격 증명, 메모리, 도구, 샌드박스와 운영 책임을 분리한다.

`ready`는 캡스톤 설계가 실습에 사용할 수 있다는 뜻이다. OpenClaw, Hermes 또는 이 구조가 기업 운영에 적합하다고 검증됐다는 뜻이 아니다.

## 진입 조건: 두 번째 업무 재사용

첫 업무의 코드를 곧바로 조직 표준으로 만들지 않는다. 다음 결과를 다른 업무에서 다시 확인한 뒤에만 이 캡스톤을 시작한다.

- 첫 업무와 사용자·도메인·예외가 다른 두 번째 업무를 구현하거나 같은 수준으로 시뮬레이션했다.
- 실행 식별자, 입력·출력 스키마, 승인·정책 이벤트, 감사 형식, 중단·복구 방식 중 무엇을 그대로 재사용했는지 기록했다.
- 업무별 권한·검수 기준·수동 SOP처럼 공통화하지 않은 항목도 남겼다.
- 두 번째 업무를 추가하며 바꾼 설정·코드·평가와 운영 부담을 측정했다.
- 두 업무의 책임자와 보안·운영 담당자가 재사용 결과와 남은 위험을 검토했다.

이 조건을 충족하지 못하면 회사 에이전트 운영 계층은 설계 검토 상태에 머문다. 첫 업무에만 맞춘 구현을 조직 표준이라고 부르지 않는다.

## 문제와 사용자

직원은 Slack이나 Teams에서 한 번에 도움을 요청하고 싶어 한다. 그러나 같은 채널을 쓴다는 이유로 서로 다른 업무의 데이터, 자격 증명, 메모리, 도구를 한 런타임 경계에 합치면 요청자 혼동이나 프롬프트 공격이 다른 업무까지 번질 수 있다.

| 사용자 | 필요한 결과 | 책임 |
|---|---|---|
| 현업 실무자 | 익숙한 채널에서 업무 요청과 상태 확인 | 원본 확인, 결과 검수, 승인 |
| 업무 책임자 | 업무별 품질·권한·중단 기준 | 실행 허용 범위와 수동 SOP 확정 |
| AX 플랫폼 팀 | 공통 진입·정책·감사·관측 기능 | 업무 셀과 런타임 어댑터 운영 |
| 원본 SaaS 소유자 | 정확한 최신 상태와 변경 기록 | API, 서비스 계정, 상태 의미 승인 |
| 보안·개인정보 담당자 | 분리된 신뢰 경계와 시크릿 수명 주기 | 권한·보유·사고 대응 검토 |
| 운영 담당자 | SLO, 장애, 업그레이드, 복구 | 중단·롤백·수동 전환 실행 |

기본 위험 수준은 `high`다. 하나의 잘못된 정책, 공유 자격 증명, 오염된 메모리, 누락된 감사 기록이 여러 업무에 동시에 영향을 줄 수 있기 때문이다.

## 기존 흐름과 목표 흐름

분산된 초기 상태:

```text
Slack·Teams 요청
→ 팀마다 다른 봇·스크립트·개인 계정
→ 각자 SaaS 조회 또는 변경
→ 런타임별 메모리·로그
→ 장애와 승인 상태를 수동 추적
```

목표 상태:

```text
공유 Slack·Teams 진입점
→ 요청자·workflow_id·요청 목적 확인
→ 외부 정책·승인 브로커
→ 업무별로 분리한 실행 셀
   ├─ 신뢰 경계
   ├─ 자격 증명
   ├─ 메모리
   ├─ 도구
   └─ 샌드박스
→ 업무의 원본 SaaS 조회 또는 승인된 변경
→ 원본 SaaS에서 실제 결과 재확인
→ 독립 감사·관측 계층에 실행 상태 기록
```

Slack과 Teams는 공통 진입점일 뿐이다. 업무의 최신 상태와 최종 변경 결과는 CRM, 문서·업무 관리 도구, 티켓 시스템 같은 **원본 SaaS가 기준**이다. 채팅 기록, 모델 답변, 런타임 메모리가 원본 SaaS를 대신하지 않는다.

## 목표와 이번 범위에서 제외한 목표

### 목표

- 공통 Slack·Teams 진입과 업무별 실행 경계를 동시에 검증한다.
- 정책·승인 판정을 런타임 밖의 브로커에서 수행하고 모든 런타임에 같은 결정을 적용한다.
- 원본 SaaS의 상태를 기준으로 읽기·쓰기 결과를 확인한다.
- 런타임과 분리한 감사·관측 계층에서 실행, 승인, 비용, 품질, 장애를 비교한다.
- OpenClaw와 Hermes를 고정된 업무에 연결하는 교체 가능한 참조 런타임 어댑터로 비교한다.

### 이번 범위에서 제외한 목표

- 하나의 에이전트·게이트웨이·메모리·서비스 계정으로 전사 사용자를 처리하는 것
- 런타임의 세션 식별자나 모델 판단을 업무 인가로 사용하는 것
- Slack·Teams 대화를 원본 업무 기록으로 승격하는 것
- 공급자 기능 목록만으로 엔터프라이즈 적합성, 규제 준수, 보안성을 판정하는 것
- 실제 조직의 운영 성과, 생산성, 비용 절감, 현업 정착을 주장하는 것

### 중단 조건

- 요청을 어떤 `workflow_id`와 신뢰 경계로 보낼지 결정할 수 없다.
- 두 업무가 자격 증명, 메모리 저장소, 변경 도구를 공유한다.
- 런타임이 외부 정책·승인 브로커를 우회해 원본 SaaS를 변경할 수 있다.
- 원본 SaaS 결과와 감사 기록이 불일치한 상태를 감지하지 못한다.
- 런타임을 멈춰도 수동 SOP로 업무를 이어 갈 수 없다.
- 업그레이드 실패 뒤 이전 버전·설정·스키마로 되돌릴 수 없다.

## 신뢰 경계와 책임 분리

| 계층 | 공통화할 것 | 업무마다 분리할 것 |
|---|---|---|
| Slack·Teams 진입 | 인증된 요청 형식, `workflow_id`, 실행 상태 표시 | 허용 채널·사용자·업무 용어 |
| 정책·승인 브로커 | 정책 판정 스키마, 승인 이벤트, 만료·철회 처리 | 역할, 한도, 금지 행동, 승인자 |
| 업무 실행 셀 | 어댑터 인터페이스, 상태·오류 형식 | 신뢰 경계, 자격 증명, 메모리, 도구, 샌드박스 |
| 원본 SaaS | 실행 식별자와 결과 대조 규칙 | API, 데이터 소유자, 완료 상태, 복구 방식 |
| 감사·관측 | 공통 이벤트 스키마와 상관관계 ID | 민감정보 마스킹, 보존 기간, 업무별 SLO |

업무 실행 셀의 분리는 채팅 세션을 나누는 데서 끝나지 않는다. 서로 신뢰하지 않는 사용자의 영향이 교차할 수 있다면 별도 프로세스·컨테이너·OS 사용자·호스트·게이트웨이 중 필요한 경계를 적용하고, 자격 증명과 메모리 저장소도 함께 분리한다.

정책·승인 브로커는 요청자, 업무, 대상, 동작, 변경 전후, 위험 등급과 승인 상태를 입력으로 받아 `allow`, `deny`, `require_approval` 중 하나를 반환한다. 런타임은 자신의 권한을 스스로 넓히거나 승인 완료를 추정하지 않는다.

독립 감사·관측 계층은 런타임의 대화 로그만 복사하지 않는다. 요청, 정책 판정, 사람 승인, 도구 호출, 원본 SaaS 결과, 복구 상태를 같은 실행 식별자로 연결하며 런타임 관리자와 분리된 열람·보존 책임을 둔다.

## 고정 업무로 런타임 어댑터 비교

두 런타임을 서로 다른 데모로 비교하지 않는다. 같은 합성 데이터와 샌드박스에서 다음 고정 업무를 수행하도록 비교 실험을 설계한다.

```text
Slack 또는 Teams에서 등록된 업무 요청
→ 원본 SaaS의 합성 레코드 조회
→ 근거가 있는 변경안 작성
→ 외부 정책 판정과 사람 승인
→ 승인된 샌드박스 변경
→ 원본 SaaS 결과 재조회
→ 독립 감사·관측 이벤트 기록
→ 장애 발생 시 중단·복구·수동 인계
```

### OpenClaw 참조 어댑터

[OpenClaw 공식 개요](https://docs.openclaw.ai/)는 여러 메시징 채널을 에이전트에 연결하는 자체 호스팅 게이트웨이와 세션·도구·멀티에이전트 라우팅을 설명한다. 이 사례에서는 그 기능을 Slack·Teams 진입 어댑터 후보로만 사용한다. — `PRIMARY_OFFICIAL`, 2026-07-27 확인

특히 [OpenClaw 공식 보안 문서](https://docs.openclaw.ai/gateway/security)는 **게이트웨이마다 하나의 신뢰할 수 있는 운영자 경계**를 가정하며, 서로 다른 신뢰 경계에는 별도 게이트웨이와 자격 증명을 사용하고 가능하면 별도 OS 사용자나 호스트까지 분리하라고 명시한다. 한 게이트웨이 안의 세션 분리는 적대적인 여러 사용자를 격리하는 인가 경계가 아니다. — `PRIMARY_OFFICIAL`, 2026-07-27 확인

따라서 업무별 신뢰가 다르면 OpenClaw 어댑터도 별도 게이트웨이·자격 증명·호스트 경계를 사용한다. 이 제약을 숨긴 채 하나의 공유 게이트웨이를 전사 멀티테넌트 경계로 취급하지 않는다.

### Hermes 참조 어댑터

[Hermes 공식 개요](https://hermes-agent.nousresearch.com/docs/)는 메시징 게이트웨이, 도구, 지속 메모리와 여러 실행 백엔드를 제공하는 에이전트 런타임을 설명한다. 이 사례에서는 같은 고정 업무를 실행하는 두 번째 참조 어댑터로만 사용한다. — `PRIMARY_OFFICIAL`, 2026-07-27 확인

[Hermes 공식 보안 문서](https://hermes-agent.nousresearch.com/docs/user-guide/security/)는 사용자 허용 목록·DM 페어링, 위험 명령 승인, 파일 쓰기 보호, 컨테이너 격리, MCP 자격 증명 필터링과 컨텍스트 파일 검사 같은 방어 계층을 설명한다. 이 통제는 런타임의 위험을 줄이는 재료지만 **업무상 인가와 승인 정책을 대신하지 않는다**. 누가 어떤 고객·프로젝트·레코드를 변경할 수 있는지는 외부 정책·승인 브로커와 원본 SaaS 권한으로 다시 결정한다. — `PRIMARY_OFFICIAL`, 2026-07-27 확인

### 비교 판정

| 비교 축 | 공통 통과 조건 |
|---|---|
| 어댑터 교체 | 정책·승인·감사 스키마와 원본 SaaS 계약을 바꾸지 않고 런타임을 교체한다. |
| 경계 분리 | 다른 업무의 자격 증명·메모리·도구·파일·세션에 접근하지 못한다. |
| 승인 우회 | 외부 브로커의 `deny` 또는 미승인 요청이 원본 SaaS 쓰기로 이어지지 않는다. |
| 결과 확인 | 런타임 응답이 아니라 원본 SaaS의 실제 상태를 완료 기준으로 사용한다. |
| 감사 완전성 | 요청부터 정책·승인·도구·결과·복구까지 같은 실행 식별자로 추적한다. |
| 실패 대응 | 프로세스 종료, 타임아웃, 부분 성공, 중복 요청 뒤 안전하게 중단·복구한다. |

향후 이 비교를 실행해 통과하더라도 “OpenClaw가 엔터프라이즈 준비를 마쳤다”거나 “Hermes가 엔터프라이즈 준비를 마쳤다”고 부르지 않는다. 그때 확인할 수 있는 범위도 고정된 샌드박스 업무와 운영 조건에 한정된다. 조직별 보안, 규제, 지원, 성능, 조달 조건은 별도 검증 대상이다.

## 운영 요구 사항

| 영역 | 설계·검증 항목 |
|---|---|
| 서비스 감독 | `systemd`, 컨테이너 오케스트레이터 또는 동등한 서비스 관리자가 시작·재시작·종료를 맡는다. 프로세스 소유자, 재시작 한도, 의존 서비스, 종료 시 큐 처리 방식을 기록한다. |
| 상태 확인과 SLO | 생존·준비 상태, 메시징 연결, 정책 브로커, 원본 SaaS, 큐 지연, 승인 지연, 쓰기 확인, 감사 적재를 각각 관측한다. 수치 목표는 업무 책임자와 합의하며 이 문서에서 임의로 정하지 않는다. |
| 시크릿 | 업무별 서비스 계정과 시크릿을 분리해 전용 저장소에서 주입한다. 메모리·프롬프트·로그·프로필 내보내기에 시크릿을 넣지 않고 회전·회수·만료를 시험한다. |
| 샌드박스 | 테스트와 실제 계정·데이터를 분리하고, 파일·네트워크·도구·리소스 허용 범위를 업무별로 제한한다. 컨테이너 하나만으로 업무 인가가 해결됐다고 보지 않는다. |
| 업그레이드·롤백 | 런타임·어댑터·정책·스키마 버전을 고정한다. 한 업무 셀에서 먼저 호환성을 검사하고, 이전 이미지·설정·메모리 마이그레이션 상태로 되돌리는 절차와 결과 대조를 남긴다. |
| 킬 스위치·수동 SOP | 업무별 쓰기 도구와 자격 증명을 즉시 차단하는 스위치, 전체 진입 중단, 대기열 동결, 읽기 전용 전환을 구분한다. 담당자는 부분 성공을 원본 SaaS와 대조한 뒤 기존 수동 절차로 이어 간다. |

서비스가 재시작됐다는 사실만으로 정상이라고 판정하지 않는다. 대표 요청을 넣어 정책 판정, 승인, 원본 SaaS 결과, 감사 이벤트까지 확인한 뒤 준비 상태로 전환한다.

## 실패 주입

정상 요청만으로 조직 운영 가능성을 판단하지 않는다.

- Slack·Teams 중복 이벤트, 잘못된 `workflow_id`, 요청자 신원 매핑 실패
- 다른 업무의 메모리·도구·자격 증명을 끌어오려는 프롬프트 공격
- 런타임 프로세스 강제 종료와 재시작 반복
- 정책 브로커 지연·장애·오래된 정책 버전
- 승인 뒤 대상·본문·도구 인자가 바뀌는 시점 경합
- 원본 SaaS 타임아웃, 속도 제한, 부분 성공, 성공 응답 유실
- 감사 저장소 장애, 이벤트 순서 뒤바뀜, 중복 적재
- 시크릿 회수·회전 중인 요청과 만료된 자격 증명
- 업그레이드 뒤 스키마·도구 호환성 실패와 롤백
- 업무별 킬 스위치, 전체 중단, 읽기 전용 전환, 수동 SOP 훈련

정책 브로커나 감사 저장소가 고위험 쓰기 전에 사용할 수 없으면 실패를 열어 두지 않고 쓰기를 차단한다. 원본 SaaS의 결과가 불명확하면 자동 재실행하지 않고 대조 큐와 담당자에게 넘긴다.

## 평가와 인수인계

평가 축:

- 두 번째 업무에서 실제 재사용한 규칙·도구와 수정·폐기한 부분
- 잘못된 업무 라우팅과 교차 경계 접근 차단
- 외부 정책·사람 승인 없는 쓰기 수: 통과 기준은 0건
- 원본 SaaS 상태와 감사 기록의 일치
- 런타임별 오류율, 지연, 비용, 자원 사용량과 운영 개입
- 장애 감지 시간, 복구 시간, 중복·누락 대조 결과
- 업그레이드·롤백 성공과 메모리·스키마 호환성
- 킬 스위치와 수동 SOP를 구현자 없이 수행할 수 있는지

인수인계 문서에는 업무 셀 소유자, 원본 SaaS 소유자, 정책 승인자, 시크릿 관리자, 런타임 운영자, 감사 열람 책임자와 대체 담당자를 적는다. 장애·승인 분쟁·데이터 삭제·공급자 교체 때 누가 최종 결정을 내리는지도 정한다.

## 결과와 한계

### 현재 결과

- 공통 진입점과 업무별 신뢰 경계를 함께 설명하는 조직 캡스톤 설계
- 외부 정책·승인 브로커, 원본 SaaS 기준, 독립 감사·관측 계층의 책임 분리
- 같은 업무로 OpenClaw·Hermes 참조 어댑터를 비교하는 판정 기준
- 서비스 감독부터 킬 스위치·수동 SOP까지의 운영·실패 주입 목록

### 아직 확인하지 못한 조건

- 두 번째 실제 업무에서 공통 규칙과 구성 요소를 재사용한 결과
- 실제 Slack·Teams 사용자와 조직 계정에서의 신원·권한·채널 운영
- 업무별 게이트웨이·자격 증명·메모리·도구 격리의 실효성
- 외부 정책·승인 브로커와 독립 감사·관측 계층의 운영
- 합의된 SLO, 장애 대응, 시크릿 회전, 업그레이드·롤백 기록
- 고정된 버전에서 수행한 OpenClaw·Hermes 비교 결과
- 조직별 보안·개인정보·법무·조달·지원 요구 충족
- 실제 현업 정착, 생산성, 품질, 비용 또는 매출 성과

확인하지 못한 항목이 남아 있는 동안 이 문서를 배포 완료나 엔터프라이즈 준비의 근거로 사용하지 않는다.

## 재사용과 다음 결정

캡스톤 뒤에도 하나의 런타임을 표준으로 고정하는 것이 기본 결론은 아니다. 다음을 각각 `공통화`, `업무별 유지`, `수정`, `폐기`로 판정한다.

- 메시징 진입과 요청 식별 규칙
- 정책·승인·감사 이벤트 스키마
- 원본 SaaS 결과 대조와 중복 방지
- 업무 셀의 격리·시크릿·메모리·도구 경계
- 서비스 감독, 상태 확인, SLO, 장애 대응
- 런타임 어댑터 인터페이스와 공급자 교체 절차

세 번째 업무로 확대하기 전에는 두 번째 업무 재사용 결과, 운영 부담, 남은 예외와 중단 기준을 독립 검토자가 다시 확인한다.
