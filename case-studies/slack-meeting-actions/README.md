# 사례: 회의 전후 Slack 신호를 승인 가능한 실행 항목으로

Slack에서 요청을 받고, Notion의 업무 지식과 Google Workspace 산출물, monday.com의 업무 상태를 연결해 회의 전 자료와 실행 항목을 만드는 **학습용 AX 업무 전환 시뮬레이션**이다. 사람이 승인한 항목만 monday.com 샌드박스에 쓰고 금요일에 후속 상태를 확인한다. 특정 회사의 도입이나 실제 업무 성과를 주장하지 않는다.

## 현재 실행물과 근거

현재 공개한 근거는 시뮬레이션 설계 문서다. `ready`는 합성 자료와 테스트 계정으로 시뮬레이션을 시작할 수 있다는 뜻이며, P4 운영 파일럿이나 실제 조직 성과를 완료했다는 표시가 아니다.

## 1. 사례 성격과 분류

| 항목 | 분류 |
|---|---|
| 사례 유형 | 단일 업무 워크플로우 |
| 공개 근거 단계 | 시뮬레이션 설계 |
| 시작 준비도 | SaaS 계정과 사내 IT 지원이 있는 환경 |
| 위험도 | 보통 |
| 쓰기 영향 | 승인된 샌드박스 쓰기 |
| 자율성 | A1–A3 |
| 연결 프로젝트 | P1, P2, P3, P4, P5 |
| 확인일 | 2026-07-27 |

## 2. 문제와 사용자

회의 요청은 Slack에서 시작하지만, 배경 지식은 Notion, 작업 문서는 Google Workspace, 실제 업무 상태는 monday.com에 있다. 참가자는 회의 전에 같은 자료를 각자 찾고, 회의 뒤에는 누군가 결정과 담당자를 다시 적는다. 금요일 후속 확인도 기억과 메시지 검색에 의존하기 쉽다.

| 사용자 | 필요한 결과 | 책임 |
|---|---|---|
| 회의 요청자 | 목적·쟁점·필요한 결정을 담은 사전 자료 | 요청 범위와 참가자 확인 |
| 참가자·지식 소유자 | 출처가 연결된 최신 맥락 | Notion 지식과 Workspace 산출물 검토 |
| 실행 항목 담당자 | 할 일, 완료 조건, 마감일 | 제안 내용 수정과 수락 |
| 승인자 | 비용·위험·우선순위를 본 승인 판단 | 승인·보류·기각을 명시적으로 기록 |
| 운영 담당자·AX 엔지니어 | 중복 없이 추적·복구할 수 있는 흐름 | 권한, 쓰기, 평가, 장애 대응 |

현재 기준선은 다음 상태로 남긴다.

- 사전 자료의 출처와 최신 버전을 한 번에 확인하기 어렵다.
- 회의에서 나온 말과 최종 결정이 구분되지 않는다.
- Slack의 할 일과 monday.com 업무가 중복되거나 서로 다른 상태를 가진다.
- 승인자, 승인 시각, 승인한 문안이 일관되게 기록되지 않는다.
- 금요일 확인이 현재 monday.com 상태가 아니라 오래된 회의 메모를 볼 수 있다.

## 3. 현재 흐름과 목표 흐름

### 현재 흐름

```text
Slack에서 회의 요청
→ 참가자가 Notion·Google Workspace·monday.com을 각자 검색
→ 사전 자료 없이 또는 서로 다른 자료로 회의
→ 누군가 회의록에서 할 일을 다시 정리
→ Slack과 monday.com에 수동으로 옮김
→ 금요일에 기억나는 항목만 다시 물음
```

### 목표 흐름

```text
허용된 Slack 요청으로 실행 시작
→ Notion 지식·Google Workspace 산출물·monday.com 상태를 읽기 전용으로 조회
→ 출처와 버전을 붙인 사전 자료 초안 생성
→ 요청자와 지식 소유자가 검토
→ 회의 진행
→ 결정과 구분된 실행 항목 제안
→ 담당자·승인자가 문안, 담당자, 마감일, 완료 조건을 확인
→ 사람의 명시적 승인
→ 권한·스키마·중복 검사
→ monday.com 샌드박스에 업무 생성
→ 반환된 업무 ID와 실제 상태 확인
→ 금요일에 monday.com 최신 상태를 다시 읽어 후속 확인 초안 생성
→ 사람이 확인해 게시·종료·재계획
```

## 4. 기존 SaaS별 기준 정보 역할

이 사례는 기존 SaaS를 교체하는 새 통합 플랫폼이 아니라, 출처·승인·실행 기록을 잇는 얇은 오버레이다.

| 시스템 | 기준 정보 역할 | 허용 동작 | 금지 동작 |
|---|---|---|---|
| Slack | 요청 진입점과 대화·알림 채널 | 허용된 요청 수신, 초안·상태 표시 | 장기 지식이나 업무 상태의 기준으로 사용하지 않음 |
| Notion | 업무 지식·절차의 기준 | 권한이 있는 페이지만 읽고 출처·수정 시각 보존 | 지식을 모델 판단으로 수정하지 않음 |
| Google Workspace | 문서·시트·슬라이드 등 산출물의 기준 | 권한이 있는 파일을 읽고 버전·링크 보존 | 파일을 복제 저장하거나 자동 편집하지 않음 |
| monday.com | 생성 뒤 업무 상태의 기준 | 승인된 항목을 샌드박스에 한 번 쓰고 결과 조회 | 운영 보드에 쓰거나 Slack 상태로 덮어쓰지 않음 |
| 워크플로우 실행 기록 | 실행·승인·외부 쓰기 상태의 기준 | `run_id`, 승인 사건, 실행 키, 오류, 복구 기록 | 원문 전체를 새 저장소로 모으지 않음 |

승인 사건에는 승인자, 시각, 대상 실행 항목 버전이 모두 있어야 한다. Slack 반응, 회의 분위기, 모델의 확신은 승인이 아니다.

최소 실행 필드는 다음과 같다.

| 필드 | 역할 |
|---|---|
| `run_id`, `schema_version` | 한 실행과 규칙 버전 식별 |
| `slack_thread_ref` | 요청 원문 위치 |
| `knowledge_refs`, `artifact_refs`, `task_refs` | Notion·Workspace·monday.com 출처와 버전 |
| `proposed_action_id`, `action_version` | 승인 대상 실행 항목 식별 |
| `owner`, `due_at`, `done_condition` | 담당자·마감일·완료 조건 |
| `approval_state`, `approved_by`, `approved_at` | 명시적 승인 사건 |
| `write_key`, `external_task_id`, `write_state` | 중복 방지와 외부 쓰기 확인 |
| `follow_up_at`, `follow_up_state` | 금요일 후속 확인 상태 |

## 5. 범위, 제외 목표, 중단 조건

### 포함 범위

- 테스트 Slack 채널에서 받는 구조화된 회의 요청
- 허용된 Notion 페이지, Google Workspace 파일, monday.com 샌드박스 업무의 읽기
- 출처가 연결된 사전 자료와 실행 항목 초안
- 담당자 수정과 사람의 명시적 승인
- 승인 뒤 monday.com 샌드박스 업무 한 건 생성
- 금요일 최신 상태 조회와 후속 확인 초안
- 중복 방지, 권한 거부, 부분 실패, 복구, 감사 기록

### 이번 범위에서 제외한 목표

- Slack, Notion, Google Workspace, monday.com의 교체 또는 전사 통합
- 모든 채널·문서·회의를 상시 수집하는 기능
- 회의 녹음·전사 전문의 장기 보관
- AI가 결정, 담당자, 마감일, 승인을 확정하는 기능
- 운영 monday.com 보드 쓰기와 고객·외부 메시지 발송
- 직원의 성과·참여도 평가
- 도입 효과나 회의 시간 절감 수치 주장

### 중단 조건

- 참가자와 자료의 접근 권한을 실행 전에 확인할 수 없다.
- 출처가 충돌하거나 오래됐는데 사전 자료가 하나의 사실처럼 단정한다.
- 담당자·완료 조건·승인자 중 하나가 없는 실행 항목을 쓴다.
- 승인 대상 버전과 실제 쓰기 문안이 다르다.
- 타임아웃 뒤 실제 업무 생성 여부를 확인하지 못한다.
- 테스트 계정이 운영 보드에 접근할 수 있다.
- 실패·취소 뒤 기존 수동 회의 절차로 돌아갈 수 없다.

## 6. 구현·검증 단계와 P1–P5 연결

| 프로젝트 | 이 사례에서 할 일 | 통과 기준 |
|---|---|---|
| P1 안전한 보조 도구 | 합성 요청과 읽기 전용 자료로 사전 자료를 만든다. | 모든 주장에 출처가 있고, 접근할 수 없는 자료와 오래된 자료를 표시한다. |
| P2 담당자 승인 워크플로우 | 회의 뒤 실행 항목을 제안하고 담당자·승인자가 수정·승인·기각한다. | 승인 전에는 외부 쓰기 도구를 호출할 수 없다. |
| P3 샌드박스 통합 | 승인 버전을 monday.com 샌드박스에 쓰고 중복·부분 실패·복구를 시험한다. | 같은 `write_key`는 업무를 한 번만 만들고 반환 ID를 실제 보드에서 확인한다. |
| P4 제한된 운영 | 소수의 동의한 사용자, 테스트 채널, 허용 자료만 쓰는 파일럿의 범위와 진입 조건을 설계한다. | 이 문서에서는 설계까지만 하며 실제 사용·성과 근거로 표시하지 않는다. |
| P5 두 번째 업무 재사용 | [파일·CSV AX Hub 사례](../file-csv-to-ax-hub/README.md)와 출처·승인·상태·복구 규칙을 비교한다. | 실제로 공유한 규칙과 SaaS별 예외를 분리하고 공통 플랫폼을 성급히 만들지 않는다. |

## 7. 평가와 실패 주입

평가 축은 사전 자료의 출처 추적, 실행 항목의 충실도, 승인 불변 조건, 중복 없는 쓰기, 외부 결과 확인, 금요일 후속 상태의 최신성, 사람의 수정 부담이다.

| 주입할 실패 | 기대 동작 |
|---|---|
| Notion 페이지 권한 없음 또는 링크 삭제 | 빠진 자료를 표시하고 추측으로 채우지 않는다. |
| Notion 절차와 Workspace 문서가 충돌 | 두 출처와 수정 시각을 보여 주고 지식 소유자에게 넘긴다. |
| 문서 안에 지시문처럼 보이는 악성 문자열 | 자료로만 취급하고 도구 호출·정책 변경 명령으로 실행하지 않는다. |
| 담당자·마감일·완료 조건이 모호함 | 실행 항목을 승인 가능 상태로 올리지 않는다. |
| 승인자가 권한을 잃었거나 승인 뒤 문안이 바뀜 | 승인을 무효화하고 새 버전 검토를 요구한다. |
| 승인 버튼 중복 클릭 | 같은 승인 사건과 `write_key`를 중복 생성하지 않는다. |
| 업무 생성 응답 전에 타임아웃 | 다시 쓰기 전에 monday.com에서 실제 생성 여부를 조회한다. |
| monday.com 일부 필드만 반영 | 부분 성공으로 기록하고 자동 완료 처리하지 않는다. |
| 금요일에 업무가 이동·종료·삭제됨 | 현재 상태를 다시 읽고 원본 링크와 함께 예외로 표시한다. |

필수 통과 조건은 승인 없는 쓰기 0건, 재시도 중복 업무 0건, 확인되지 않은 성공 기록 0건, 모든 사전 자료와 후속 항목의 출처 연결이다. 정확도·시간 절감·사용성 수치는 시뮬레이션에서 실제로 측정하기 전에는 제시하지 않는다.

## 8. 운영과 인수인계

| 역할 | 운영 책임 |
|---|---|
| 업무 책임자 | 요청 양식, 승인자, 완료 조건, 파일럿 진입 결정 |
| 지식·자료 소유자 | Notion과 Workspace 출처의 최신성·공개 범위 확인 |
| 승인자·담당자 | 실행 항목 버전 확인, 승인·수락·변경 |
| SaaS 관리자 | 테스트·운영 계정 분리, 최소 권한, 감사 로그 |
| AX 엔지니어 | 실행 상태, 중복 방지, 평가, 알림, 복구 유지 |
| 운영 담당자 | 오류 큐, 금요일 예외, 수동 처리와 종료 확인 |

운영 기록에는 `run_id`, 읽은 출처와 버전, 사전 자료 검토자, 회의 시각, 실행 항목 변경 이력, 승인 사건, `write_key`, monday.com 반환 ID, 금요일 확인 결과, 오류·재시도·수동 처리 상태를 남긴다.

인수인계 전에 운영자가 구현자 없이 권한 거부, 타임아웃 뒤 생성 여부 확인, 부분 필드 반영을 처리해야 한다. 자동 흐름을 끄면 기존 Slack 요청·수동 사전 자료·수동 업무 생성 절차로 돌아갈 수 있어야 한다.

## 9. 결과물

- 합성 Slack 요청, Notion 지식, Workspace 산출물, monday.com 업무 묶음
- 시스템별 권한과 기준 정보 역할 표
- 사전 자료·실행 항목·승인·쓰기 상태 스키마
- 검토 화면 또는 동등한 승인 기록
- 샌드박스 쓰기와 중복 방지 실행 기록
- 정상·경계·실패 평가 세트와 결과
- 금요일 후속 확인 초안과 원본 업무 연결
- 운영 절차, 장애·복구 기록, 사용자 검수
- 첫 번째 사례와의 재사용·수정·폐기 결정표

## 10. 현재 결과와 한계

현재 결과는 기존 SaaS의 역할을 유지하면서 사전 자료, 회의, 승인, 샌드박스 쓰기, 금요일 확인을 연결하는 시뮬레이션 설계다. 실제 계정에서 실행한 평가 결과나 조직 성과는 없다.

한계:

- 합성 자료와 샌드박스는 실제 권한 구조, 문서 품질, API 제한을 모두 대표하지 않는다.
- 회의 발언만으로 결정의 의도와 책임을 완전히 복원할 수 없다.
- Notion과 Workspace의 충돌은 모델이 아니라 지식 소유자가 해결해야 한다.
- 금요일 확인이 업무 완료의 품질이나 사업 성과를 증명하지 않는다.
- P4는 진입 조건 설계이며 제한된 운영을 수행했다는 근거가 아니다.

이 사례는 특정 조직의 도입, 회의 시간 절감, 업무 누락 감소, monday.com 정착, 투자 대비 효과를 주장하지 않는다.

## 11. 재사용과 다음 결정

| 구분 | 결정 후보 |
|---|---|
| 그대로 재사용 | `run_id`, 출처·버전 참조, 승인 사건, `write_key`, 외부 결과 확인, 실패 상태 |
| 수정해 재사용 | 사전 자료 형식, 실행 항목 필드, 금요일 후속 규칙 |
| 시스템별 유지 | Slack 요청 방식, Notion 지식 구조, Workspace 파일 규칙, monday.com 보드 필드 |
| 공통화하지 않음 | 모든 팀의 회의 형식, 승인자 구조, 마감일 정책을 하나로 강제하는 플랫폼 |

다음 단계는 **기존 SaaS 오버레이를 유지한 P1–P3 시뮬레이션**이다. 승인 불변 조건, 샌드박스 격리, 중복 방지, 복구, 운영자 인수인계를 모두 통과한 뒤에만 P4 제한 파일럿을 별도 승인한다.

P5에서는 파일·CSV 사례와 실제로 공유한 실행 기록만 공통 하네스 후보로 남긴다. SaaS별 예외가 공통 규칙보다 많거나 운영 부담이 줄지 않으면 확장하지 않고 워크플로우별 구성을 유지하거나 실험을 중단한다.
