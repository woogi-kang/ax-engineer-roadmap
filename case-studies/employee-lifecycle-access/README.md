# 사례: 입사·이동·퇴사에 맞춘 계정·권한 운영

직원 정보가 바뀌면 계정, 권한, 장비, 첫 주 업무도 함께 바뀌어야 한다. 이 사례는 안내문 생성이 아니라 필요한 변경을 빠짐없이 준비하고, 담당자가 승인한 범위만 테스트 시스템에 반영하며, 취소나 퇴사 시 되돌릴 수 있는 흐름을 다룬다.

## 1. 사례 성격과 현재 근거

- 유형: 업무 흐름
- 도메인: 사람·협업
- 현재 단계: 시뮬레이션 설계
- 연습 범위: P1~P5
- 외부 영향: 승인 후 샌드박스 계정·권한 변경

`ready`는 이 문서로 실습을 시작할 수 있다는 뜻이다. 실제 조직의 계정을 발급하거나 회수했고, 온보딩 시간이나 보안 위험이 줄었다는 뜻은 아니다.

## 2. 문제와 사용자

| 항목 | 내용 |
|---|---|
| 시작 사건 | 입사 확정, 부서·직무 이동, 휴직·복직, 퇴사 확정 |
| 주요 사용자 | People Ops, 채용 담당자, 매니저, IT·보안 담당자, 신규 구성원 |
| 업무 책임자 | 직원 상태는 People Ops, 업무 권한은 매니저와 데이터 소유자, 계정 실행은 IT·보안 |
| 자주 생기는 문제 | 요청 누락, 과도한 권한, 입사 취소 뒤 계정 잔존, 퇴사 뒤 회수 지연, 완료 여부 확인 어려움 |
| 실패 피해 | 업무 시작 지연, 민감정보 노출, 라이선스 낭비, 감사 기록 누락 |

## 3. 현재 흐름과 목표 흐름

```text
현재
입사·변경 정보를 메일이나 메신저로 전달
→ 담당자가 시스템마다 같은 정보를 다시 입력
→ 권한 승인과 계정 생성이 따로 진행
→ 누락 여부를 사람이 기억으로 확인

목표
확정된 직원 상태 수신
→ 신원·직무·시작일과 변경 버전 확인
→ 필요한 계정·권한·장비·업무 목록 초안
→ 매니저·데이터 소유자·IT 승인
→ 샌드박스에 멱등하게 반영
→ 실제 상태 대조와 완료 기록
```

입사 취소, 직무 변경, 퇴사일 변경은 새 요청으로 덮어쓰지 않는다. 앞 요청과의 관계를 남기고, 이미 실행된 변경을 회수하거나 보상할 절차를 함께 만든다.

## 4. 시스템별 기준 정보

| 시스템 | 기준으로 삼을 정보 | 맡기지 않는 판단 |
|---|---|---|
| HRIS·채용 시스템 | 직원 식별자, 고용 상태, 소속, 시작·종료일 | 업무 권한의 필요성 |
| IdP·조직 계정 | 실제 계정 상태, 그룹, 세션, MFA | 인사 상태 판단 |
| 업무 SaaS | 워크스페이스·프로젝트 권한과 라이선스 | 고용 상태 판단 |
| ITSM·MDM | 장비와 지원 요청의 상태 | 권한 승인 |
| Slack·메일 | 승인 요청과 알림 | 직원 상태의 원본 |
| 감사 저장소 | 요청·승인·실행·회수 사건 | 원본 시스템 대체 |

## 5. 업무 실행 규칙

모든 요청에는 `employee_id`, `lifecycle_event`, `effective_at`, `role_version`, `request_id`를 둔다. 실행 전에는 같은 `request_id`가 처리됐는지, 직원 상태가 요청 생성 뒤 바뀌지 않았는지 다시 확인한다.

- AI는 필요한 작업과 근거를 정리하고 누락·충돌을 표시한다.
- 매니저는 업무 역할과 프로젝트 접근을 승인한다.
- 데이터 소유자나 보안 담당자는 민감 시스템 접근을 별도로 승인한다.
- IT 실행자는 승인된 변경만 샌드박스에 반영한다.
- 고위험 관리자 권한과 실제 운영 계정은 자동으로 부여하지 않는다.

## 6. P1~P5 실습 경로

| 단계 | 실습 | 통과 기준 |
|---|---|---|
| P1 | 합성 직원 사건에서 필요한 작업 초안 만들기 | 누락·중복·직무 충돌 평가 사례 통과 |
| P2 | 승인자별 검토 화면과 변경 전후 비교 | 승인·수정·거절과 사유가 기록됨 |
| P3 | IdP·SaaS 샌드박스 계정 발급·회수 | 중복 실행, 부분 실패, 입사 취소 복구 시험 |
| P4 | 낮은 권한의 제한된 파일럿 설계 | 수동 처리, 중단, 인수인계 기준이 준비됨 |
| P5 | 다른 권한 변경 업무에서 규칙 재사용 | 재사용한 계약과 새로 추가한 예외가 구분됨 |

## 7. 평가와 실패 복구

| 실패 주입 | 확인할 것 | 복구 |
|---|---|---|
| 같은 사람이 두 번 등록됨 | 신원 충돌을 실행 전에 막는가 | 검토 대기열로 보내고 수동 병합 |
| 입사일 직전 취소됨 | 생성된 계정과 장비 요청을 찾는가 | 계정 비활성화·요청 취소·토큰 회수 |
| 직무가 승인 중 바뀜 | 오래된 승인으로 쓰기를 막는가 | 새 역할 버전으로 재승인 |
| 일부 SaaS만 성공함 | 부분 성공 상태를 숨기지 않는가 | 성공 항목 유지 여부를 결정하고 나머지 재시도 |
| 퇴사 회수가 실패함 | 고위험 접근을 우선 차단하는가 | 세션·토큰 차단 후 수동 회수 절차 실행 |

운영 지표는 계정 생성 수보다 승인 대기시간, 수정 부담, 부분 실패율, 퇴사 후 잔존 권한, 수동 복구 시간을 본다.

## 8. 결과물과 한계

이 사례에서 공개할 결과물은 합성 직원 사건, 역할별 권한표, 승인 기록, 샌드박스 실행 로그, 실패 주입 결과, 회수 훈련 기록이다.

아직 실제 조직의 계정·장비 시스템과 연결하지 않았다. 회사마다 역할, 승인자, 계정 구조, 라이선스, 노무·보안 절차가 다르므로 이 설계를 그대로 운영 절차로 사용하지 않는다.

## 9. 재사용과 다음 결정

재사용 후보는 직원 사건 스키마, 승인표, 멱등 실행 키, 부분 실패 상태, 회수 절차다. 실제 두 번째 권한 업무에서 같은 규칙을 사용해 본 뒤에만 공통 계정 운영 구성 요소로 올린다.
