# 사례: 매출 근거에서 전자세금계산서 발행·입금 대사까지

## 현재 범위와 설계 목표

| 구분 | 쓰기 영향 | 자율성 | P 단계 |
|---|---|---|---|
| 현재 공개 실행물 | 외부 쓰기 없음 | A0 | 없음 |

현재 값은 이 저장소에서 재현할 수 있는 범위만 나타낸다. 설계 목표는 아직 구현 범위나 조직 운영 성과가 아니다.

> 공개 사례 연결: K03의 생성형 추천과 결정론적 규칙 분리 원칙을 [공개 사례 적용 맵](../../research/public-case-application-map.md)에서 세무 규칙·승인·발행 통제로 연결했다.

전자세금계산서 업무는 문서를 한 장 만드는 데서 끝나지 않는다. 계약·주문·검수와 회계 상태를 확인하고, 담당자가 발행 내용을 승인하며, 발행·전송 결과와 입금 상태를 다시 맞춰야 한다. 이 사례는 그 전체 흐름을 합성 데이터와 테스트 환경에서 연습한다.

## 현재 실행물과 근거

현재 공개한 근거는 시뮬레이션 설계 문서다. 실제 전자세금계산서를 발행·정정·취소·전송하지 않으며, 과세 여부, 면세 여부, 작성일, 수정 사유, 신고 처리는 회사의 세무 책임자나 세무대리인이 결정한다.

## 1. 사례 성격

- 유형: 업무 흐름
- 도메인: 재무·구매
- 연습 범위: P1~P4
- 외부 영향: 담당자 승인 뒤 전자세금계산서 공급자 샌드박스에만 쓰기

## 2. 문제와 사용자

| 항목 | 내용 |
|---|---|
| 시작 사건 | 계약상 청구 조건 충족, 납품·검수 완료, 회계 담당자의 발행 요청 |
| 주요 사용자 | 영업운영, 재무·회계, 세무 책임자, 채권 담당자 |
| 업무 책임자 | 거래 근거는 영업·운영, 발행과 회계 처리는 재무·세무, 입금 확인은 채권 담당자 |
| 자주 생기는 문제 | 금액·공급일 불일치, 중복 발행, 거래처 정보 오류, 발행 결과 누락, 입금 미대사 |
| 실패 피해 | 잘못된 증빙, 정정 업무 증가, 회계 상태 불일치, 수금 지연 |

## 3. 목표 흐름

```text
계약·주문·검수 근거 수집
→ 거래처·공급일·공급가액·세액·중복 여부 점검
→ 근거가 연결된 발행 초안 생성
→ 회계·세무 책임자 승인
→ 전자세금계산서 공급자 샌드박스에 발행 요청
→ 발행·전송 결과를 ERP 상태와 대조
→ 은행 입금과 채권을 대사
→ 불일치·미입금·부분 실패를 담당자 대기열로 전달
```

## 4. 시스템별 기준 정보

| 시스템 | 기준으로 삼을 정보 | 주의할 점 |
|---|---|---|
| 계약·주문·검수 | 거래와 청구 조건의 근거 | 문서만으로 세무 판단을 자동 확정하지 않음 |
| ERP·회계 | 매출·채권·회계 처리 상태 | 발행 결과를 대신하지 않음 |
| 전자세금계산서 공급자·발행 결과 | 발행 요청과 실제 처리 결과 | 응답 시간 초과를 실패로 단정하지 않음 |
| 은행 거래내역 | 입금 상태 | 유사 금액을 자동으로 같은 채권에 매칭하지 않음 |
| Slack·메일 | 승인 요청과 알림 | 거래·발행·입금의 기준 정보가 아님 |

국세청은 홈택스에서 전자(세금)계산서를 발급할 수 있다고 안내하고 있으며, 별도 시스템사업자에 대해서는 발급·전송과 이용자 보호 기준을 고시한다. 이 사례는 특정 공급자를 권장하지 않고, 실제 연동 전 현재 제도와 공급자 문서를 다시 확인한다. ([국세청 사업자용 간편인증 안내](https://s.nts.go.kr/yeoksam/na/ntt/selectNttInfo.do?mi=5913&nttSn=1352014), [전자(세금)계산서 시스템사업자 고시](https://s.nts.go.kr/nts/na/ntt/selectNttInfo.do?mi=2205&nttSn=1351085), 2026-07-31 확인)

## 5. 업무 실행 규칙

발행 후보에는 `transaction_id`, `customer_id`, `evidence_version`, `supply_date`, `supply_amount`, `tax_amount`, `issue_key`를 둔다.

- `issue_key`가 같으면 새 발행을 만들지 않고 기존 요청과 결과를 조회한다.
- 금액, 날짜, 거래처 정보, 증빙 버전이 승인 뒤 바뀌면 승인을 무효화한다.
- AI는 누락과 불일치를 표시하고 초안을 만들 수 있지만 과세·면세와 수정 사유를 결정하지 않는다.
- 발행, 정정, 취소, 신고, 납부는 책임자의 승인 없이 실행하지 않는다.
- 은행 대사는 금액만으로 확정하지 않고 입금자, 일자, 참조번호와 허용 오차를 함께 본다.

## 6. P1~P4 실습 경로

| 단계 | 실습 | 통과 기준 |
|---|---|---|
| P1 | 합성 거래에서 발행 후보와 오류 찾기 | 중복·금액·날짜·거래처 오류 평가 통과 |
| P2 | 근거가 보이는 발행 초안과 승인 화면 | 수정·거절 사유와 변경 전후가 기록됨 |
| P3 | 공급자·ERP 샌드박스 연동 | 중복 요청, 시간 초과, 부분 실패, 재조회 시험 |
| P4 | 제한된 운영 파일럿 계획 | 세무 책임자 승인, 수동 발행, 중단·복구 기준 준비 |

## 7. 실패 주입과 복구

| 실패 주입 | 확인할 것 | 복구 |
|---|---|---|
| 같은 거래가 두 번 들어옴 | `issue_key`로 중복을 막는가 | 기존 요청과 결과를 연결 |
| 승인 뒤 금액이 바뀜 | 오래된 승인을 무효화하는가 | 새 버전으로 재검토 |
| 공급자 응답이 늦음 | 재시도 전에 실제 처리 결과를 조회하는가 | 상태 조회 후 미처리일 때만 재시도 |
| 발행 성공, ERP 반영 실패 | 부분 성공을 별도 상태로 남기는가 | 발행 결과를 기준으로 ERP 보정 대기열 생성 |
| 입금액이 여러 채권과 비슷함 | 자동 확정을 멈추는가 | 담당자 대사 대기열로 이동 |

## 8. 결과물과 한계

공개 결과물은 합성 계약·매출·채권·입금 데이터, 발행 초안, 승인표, 중복 방지 시험, 부분 실패·복구 기록이다.

이 설계는 세무 자문이나 신고 절차가 아니다. 실제 회사의 과세 유형, 발행 의무, 수정 방식, 보관·신고 기준은 현재 법령과 책임자의 판단을 따라야 한다. 운영 성과와 정확도는 확인하지 않았다.

## 9. 재사용과 다음 결정

거래 식별자, 근거 버전, 승인 무효화, 멱등 발행 키, 외부 결과 재조회, 채권 대사 규칙은 다른 청구·정산 업무에서도 시험할 수 있다. 실제 두 번째 거래 업무에서 재사용한 항목만 공통 결제·정산 구성 요소로 올린다.
