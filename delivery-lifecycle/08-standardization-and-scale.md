# 8. 표준화와 확장

## 목적

한 업무에서 확인한 규칙과 도구를 다른 업무에 적용해 보고, 함께 쓸 부분과 업무별로 달라야 할 부분을 구분한다.

## 주요 작업

1. 첫 사례의 실행 규칙·구성 요소·운영 절차를 목록으로 만든다.
2. 두 번째 업무에서 그대로 재사용할 부분, 설정만 바꿀 부분, 새로 구현할 부분으로 나눈다.
3. 공통으로 쓸 입력·출력·평가·승인·기록 규격을 찾아낸다.
4. 팀별 기술 선택과 공통 운영 기준의 경계를 정한다.
5. 버전·호환성·폐기 정책을 만든다.
6. 반복되는 운영 실패를 재현해 공통 도구나 플랫폼의 개선 과제로 남긴다.
7. 다음 투자 대상마다 확장·개선·유지·중단 중 하나를 결정한다.

## 재사용 절차를 변경할 때

문서, 공통 코드, Skill 중 어느 형태로 보관하든 유지 담당자와 검수할 업무를 정한다. Skill을 선택했다면 [P5의 업무 A/B 비교](../projects/05-second-workflow-reuse.md#skill-재사용을-선택한-경우)와 [재사용 검수 카드](../toolkit/reusable-skill-card.md)를 사용한다. 적용·비적용 조건, 출처, 라이선스, 의존성과 설치 검토를 기록하고 실제 권한은 업무별로 유지한다.

공통 절차가 바뀌면 사용하는 업무를 찾아 각각 회귀 평가한다. 한 업무에서 통과한 결과로 다른 업무의 검수를 대신하지 않는다. 오래된 자료를 갱신할 담당자, 배포를 보류할 조건, 이전 버전 복원과 진행 중인 작업의 처리도 정한다. 변경·설치 기록과 실제 외부 결과의 대사는 따로 남긴다.

## 공통 하네스의 최소 범위

공통 하네스는 모든 팀에 같은 프레임워크나 화면을 강제하기 위한 것이 아니다.

- 기준 데이터와 문서 위치
- 입력·출력 규격
- 완료·품질 검증
- 담당자 승인 지점
- 권한과 실행 정책
- 감사·변경·버전 기록
- 실패 탐지와 복구
- 비용과 운영 상태 확인

## 산출물

- 사례 간 재사용 비교
- 공통 실행 규칙과 업무별 추가 항목
- 버전·호환성 정책
- 플레이북과 재사용 모듈
- 공통 도구·플랫폼 개선 과제
- 다음 업무 투자 결정
- 재사용 절차의 소유자·지원 업무·버전·출처·라이선스와 변경 영향 목록
- Skill을 검토했다면 채택·비채택 근거. 채택해 실행을 시험했다면 업무별 적용·비적용·실패 시험과 회귀·롤백 기록

## 통과 기준

- 두 번째 업무에서 무엇을 실제로 재사용했는지 결과로 설명한다.
- 공통화하지 않은 예외와 이유가 기록돼 있다.
- 새 업무를 추가할 때마다 중앙 팀이 수작업으로 복제하지 않는다.
- 현업이 허용된 범위에서 설정·평가·운영을 조정할 수 있다.
- 공통 기반의 변경이 기존 업무에 미치는 영향을 평가한다.
- 재사용 절차를 적용하지 않을 조건과 업무별 예외가 남아 있다.
- 출처·의존성·라이선스를 검토했고 변경·폐기·복원 책임자를 정했다.
- Skill을 채택한 경우 오활성화·충돌·권한 확대를 시험하고 두 업무의 회귀·롤백 결과를 확인했다.

## 중단 신호

- 첫 사례를 근거로 전사 표준을 확정한다.
- 재사용보다 추상화 비용이 더 크다.
- 모든 예외를 공통 기능에 포함한다.
- 기반 팀이 현업 문제와 사용자 피드백에서 멀어진다.
- 확장할 이유보다 이미 만든 자산을 활용해야 한다는 이유가 앞선다.
- 어느 업무가 어떤 버전의 절차를 쓰는지 알 수 없거나 이전 버전으로 되돌릴 수 없다.
