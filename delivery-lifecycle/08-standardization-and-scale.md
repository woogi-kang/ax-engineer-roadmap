# 8. 표준화와 확장

## 목적

한 업무에서 확인한 규칙과 도구를 다른 업무에 적용해 보고, 함께 쓸 부분과 업무별로 달라야 할 부분을 구분한다.

## 주요 작업

1. 첫 사례의 실행 규칙·구성 요소·운영 절차를 목록으로 만든다.
2. 두 번째 업무에서 그대로 재사용, 설정 변경, 새 구현으로 나눈다.
3. 공통 입력·출력·평가·승인·기록 규격을 추출한다.
4. 팀별 기술 선택과 공통 운영 기준의 경계를 정한다.
5. 버전·호환성·폐기 정책을 만든다.
6. 반복되는 운영 실패를 재현해 공통 도구나 플랫폼의 개선 과제로 남긴다.
7. 다음 투자 대상을 확장·개선·유지·중단으로 결정한다.

## 공통 하네스의 최소 범위

공통 하네스는 모든 팀에 같은 프레임워크나 화면을 강제하기 위한 것이 아니다.

- 기준 데이터와 문서 위치
- 입력·출력 규격
- 완료·품질 검증
- 담당자 승인 지점
- 권한과 실행 정책
- 감사·변경·버전 기록
- 실패 탐지와 복구
- 비용과 운영 상태 확인

## 산출물

- 사례 간 재사용 비교
- 공통 실행 규칙과 업무별 추가 항목
- 버전·호환성 정책
- 플레이북과 재사용 모듈
- 공통 도구·플랫폼 개선 과제
- 다음 업무 투자 결정

## 통과 기준

- 두 번째 업무에서 무엇을 실제로 재사용했는지 결과로 설명한다.
- 공통화하지 않은 예외와 이유가 기록돼 있다.
- 새 업무 추가가 중앙 팀의 수작업 복제로만 이루어지지 않는다.
- 현업이 허용된 범위에서 설정·평가·운영을 조정할 수 있다.
- 공통 기반의 변경이 기존 업무에 미치는 영향을 평가한다.

## 중단 신호

- 첫 사례를 근거로 전사 표준을 확정한다.
- 재사용보다 추상화 비용이 더 크다.
- 모든 예외를 공통 기능에 포함한다.
- 기반 팀이 현업 문제와 사용자 피드백에서 멀어진다.
- 확장할 이유보다 이미 만든 자산을 활용해야 한다는 이유가 앞선다.
