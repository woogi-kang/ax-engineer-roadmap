# 출처 정책

## 목적

AX Engineer의 역할과 기술 환경은 빠르게 바뀐다. 이 저장소는 기억이나 유행보다 확인 가능한 근거를 우선하고, 사실·경험·가설을 구분한다.

## 출처 유형

| 표기 | 의미 | 사용 예 |
|---|---|---|
| `PRIMARY_OFFICIAL` | 회사·프로젝트·기관의 공식 원문 | 채용 공고, 공식 문서, 표준 |
| `PRIMARY_REPOSITORY` | 공개 저장소의 실제 파일 | README, 기여 규칙, 코드 |
| `PUBLIC_RESEARCH` | 논문·공공 보고서·검증 가능한 연구 | 평가·보안·조직 연구 |
| `PRACTITIONER_EVIDENCE` | 재현 가능한 현장 산출물과 운영 기록 | 평가 결과, runbook, 장애 기록 |
| `PUBLIC_SECONDARY` | 기사·블로그·요약 자료 | 시장 동향과 보조 설명 |
| `HYPOTHESIS` | 아직 검증하지 않은 적용 가설 | 사례의 예상 병목 |
| `UNKNOWN` | 정보가 없거나 상충해 보류 | 조직 책임자, 실제 기준선 |

## 우선순위

1. 직무 정의는 현재 회사의 공식 채용·팀 설명을 우선한다.
2. 기술 동작은 공식 문서와 실제 버전을 확인한다.
3. 공개 프로젝트 평가는 README 요약보다 실제 파일을 읽는다.
4. 기사와 개인 글은 보조 근거로 사용한다.
5. 성과 수치를 인용할 때는 발표 주체, 관측기간, 표본·분모, 방법과 한계를 붙인다. 빠진 조건은 미공개로 표시하고 자체 발표를 검증된 효과로 바꾸지 않는다.

## 링크 작성

- 링크가 뒷받침하는 주장 가까이에 둔다.
- 변경 가능성이 큰 자료에는 `YYYY-MM-DD 확인`을 표시한다.
- 링크 제목만으로 출처를 평가하지 않는다.
- 접근할 수 없는 링크는 대체 출처를 찾거나 `UNKNOWN`으로 표시한다.

## 사례 공개

- 회사·고객·동료를 식별할 수 있는 정보를 제거한다.
- 공개 자료와 비공개 경험을 섞지 않는다.
- 실제 사례를 일반화하면 무엇을 바꿨는지 적는다.
- 데이터 수집 범위와 누락·편향을 함께 공개한다.
- 실패한 실험도 중단 조건과 배운 점을 구체적으로 적었다면 포함할 수 있다.

## 업데이트

출처가 오래됐거나 현재 내용과 다르면 `Source update` Issue를 연다. PR에는 이전 주장, 새 근거, 독자에게 미치는 변화를 적는다.

외부 링크는 매주 자동 확인한다. 명확한 `404`·`410`은 실패로 처리한다. 그 밖의 비정상 응답은 로그인·봇 차단·요청 제한 같은 `4xx`, 일시적인 `5xx`, 네트워크 오류를 구분해 경고와 수동 확인 대상으로 남긴다. 공개 사례의 출처 유형·도입 단계·성과 검증 상태는 [`public-ax-cases.json`](public-ax-cases.json)을 기준으로 관리한다. 2026-10-26 현재 사례 40개, 고유 원문 URL 54개이며 기존 사례 25개와 원문 26개를 보존했다. 새 출처를 읽고 내용을 갱신하는 작업은 링크 상태 검사와 별개다.

## 날짜와 주장 단위의 기록

기술 문서는 제안·초안·선택 확장·정식 명세·폐기 예정 상태를 구분한다. 명세가 공개됐어도 사용하는 Host·Server·SDK에서 지원하는지는 따로 확인한다. 향후 계획과 실제 구현을 구분하는 검토 절차는 [표준과 제안의 검토 목록](standards-watchlist.md)을 따른다.

게시일, 확인일과 관측기간은 다르다. `2026-10-26`에 읽었다는 사실만으로 8~10월의 시장 변화라고 쓰지 않는다. 기준일 이후 발표라도 조사 대상 기간이 그 이전이면 그 기간을 함께 적는다.

| 구분 | 기록 기준 |
|---|---|
| 기준일 이후 발표 | 원문 게시일이 비교 기준일 뒤임을 확인했다. 발표일과 실제 관측기간을 따로 적는다. |
| 날짜 없는 현재 신호 | 원문은 읽었지만 게시일을 모른다. 신설·증가·감소의 증거로 쓰지 않는다. |
| 기존에 빠진 근거 | 게시일이 기준일 이전이다. 새 변화와 분리해 기존 판단을 다시 검토한다. |
| 과거 자료 | 예전 확인 내용과 원래 출처를 보존한다. 현재 모집·운영·성과 상태는 보장하지 않는다. |
| `unknown` | 원문을 읽지 못했거나 자료가 상충한다. 빈칸을 추정으로 채우지 않는다. |

[`public-ax-cases.json`](public-ax-cases.json)의 `verified_at`은 최초 25개 사례의 기준일 `2026-08-01`을 보존한다. `review_scope.baseline_case_ids`로 당시 목록을 고정하고, `updated_at`과 `review_scope`로 이번 검토 범위를 기록한다. 2026-10-26에는 기존 25개 모두 확인을 시도해 24개의 주요 본문을 읽었으며 K06은 접근 실패로 보류했다. 원문 재확인은 회사의 현재 운영 상태나 발표 성과를 독립 검증했다는 뜻이 아니다.

추가 사례는 `introduced_at`과 `initial-review` 주장으로 첫 검토 시점을 기록한다. 직접 읽은 출처가 있어야 하며 과거 기준일의 `baseline-summary`를 만들어 넣지 않는다. 기존 사례의 후속 확인은 `source-confirmation`, 내용 수정은 근거와 함께 정정 주장으로 남긴다.

각 `claims` 항목에는 주장, 출처 URL, 발행·확인 날짜, 원문 접근 상태, 시간 분류, 관측기간, 표본, 방법과 한계를 둔다. 모르는 날짜와 표본 크기는 `null`로 남기고 설명에 빠진 조건을 적는다. `source-reported`는 원문에 그렇게 적혀 있음을, `study-reported`는 해당 표본·방법의 연구 보고를 뜻한다. 둘 다 독립 검증 등급을 자동으로 높이지 않는다. 원문 미확인 후속 주장은 `unknown`으로 둔다.

기존 26개 URL은 각 사례의 `source_urls`와 baseline 주장에 보존한다. 추가 사례와 후속 주장까지 포함한 고유 URL은 54개다. 검사는 날짜의 실제 유효성, 원문·관측기간의 시간 순서, 검토 범위, 한영 문서의 주장 ID·링크와 분류값을 확인한다. 링크 검사 통과는 원문 내용이나 성과의 검증을 대신하지 않는다.

`baseline_deployment_stage`는 기존 사례의 기준 분류 또는 추가 사례의 첫 분류를 보존한다. 원문과 다른 분류는 `deployment_correction`의 `from`(기존 기준), `to`(정정한 분류), 한영 사유와 근거를 남겨 고친다. 현재 분류가 기준과 다르면 이를 뒷받침하는 읽은 정정 주장이 필요하며 과거 정정 기록도 보존한다. `not-rechecked`는 이번에 후속 주장을 추가하지 않았음을 나타낸다. `selected-claims-reviewed`와 `initial-claims-reviewed`도 기록한 주장만 검토했다는 뜻이다.

## 채용 공고의 상태와 중복

[`hiring-signals.json`](hiring-signals.json)은 공고 본문, 원문 접근 상태, 모집 표시와 게시일을 각각 기록한다. `added_at`은 목록에 넣은 날짜다. 게시일을 모르면 `null`로 두며 최근 공고로 집계하지 않는다.

- `open`: 직접 읽은 원문에서 해당 직무의 지원 경로나 명시적 모집 상태를 확인했다. 지원 제출 성공을 뜻하지 않는다.
- `closed`: 명시적인 마감 표시 또는 지난 마감일을 확인했다. 마감 표시는 상시채용 문구나 미래 마감일보다 우선한다.
- `unknown`: 접수 경로가 불명확하거나 원문을 읽지 못해 상태를 정하지 못했다.
- `conflicting`: 동일 공고임을 확인한 출처들이 서로 다른 모집 상태를 보인다.

원 공고 ID가 확인되면 같은 공고의 출처를 묶는다. 회사·직함만 같고 ID 대응이 불명확하면 `related_sources`에 관계와 한계를 남기고 상태 집계에서 제외한다. 따라서 레코드 수는 고유 채용 건수나 신규 일자리 수가 아니다. [이번 갱신 기록](evidence-refresh-2026-10-26.md)에 검색 범위, 제외·보류 이유와 접근 실패를 남겼다.
