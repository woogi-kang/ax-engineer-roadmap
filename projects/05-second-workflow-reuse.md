# 프로젝트 5. 두 번째 업무 재사용

## 목표

첫 프로젝트의 코드를 곧바로 전사 표준으로 정하지 않는다. 다른 업무에서 실제로 재사용할 수 있는 실행 규칙과 구성 요소를 확인한 뒤 공통 하네스의 범위를 정한다.

## 진입 조건과 결과 범위

P1~P3의 통과 근거와 [P4 실전 통과 또는 시뮬레이션 검증](04-production-pilot.md)을 확인한다. 어느 경로든 실패·복구·독립 검수 기록이 필요하다. 선택한 사례에 P4가 없으면 별도 운영 실습이나 시뮬레이션으로 채울 수 있다. 다른 업무에서 수행한 P4 근거는 원래 업무·환경·버전을 밝히고 이번 업무의 데이터·권한·예외·복구 조건에 적용할 수 있는지 검토받는다. 일치하지 않는 필수 조건은 새로 시험하며 과거 승인을 이전하지 않는다. P4 근거가 없다면 재사용 후보를 설계할 수는 있지만 P5 실행 검증을 마쳤다고 표시하지 않는다.

두 번째 업무는 새 데이터·권한·승인·평가 조건을 확인한다. 첫 업무의 승인이나 통과 기록을 그대로 적용하지 않는다. 시뮬레이션 경로는 실제로 시험한 코드·절차의 재사용만 주장하고 조직 간 확산이나 현업 운영 성과는 미검증으로 남긴다.

## 두 번째 업무 선택

첫 업무와 완전히 같지 않으면서 다음 요소 중 일부를 공유하는 업무를 고른다.

- 같은 원본 시스템
- 비슷한 승인 구조
- 같은 평가 실행 방식
- 비슷한 외부 실행·복구
- 다른 부서·사용자·도메인 용어

두 업무 사이에 차이가 있어야 첫 업무에만 맞춘 잘못된 추상화를 발견할 수 있다.

## 비교할 항목

| 영역 | 질문 |
|---|---|
| 목표·업무 | 첫 업무의 성공 기준을 그대로 강제하지 않았는가? |
| 데이터 | 공통 식별자와 데이터 출처 규칙이 재사용되는가? |
| 입력·출력 | 스키마의 공통 필드와 도메인 확장 필드는 무엇인가? |
| 평가 | 실행 방식은 같아도 판정 기준은 도메인별로 남는가? |
| 승인·권한 | 공통 이벤트와 역할별 결정권을 분리했는가? |
| 기록·관측 | 같은 실행 식별자와 상태 모델로 추적할 수 있는가? |
| 복구 | 공통 중단·인계 구조와 업무별 수동 절차를 나눴는가? |
| UI·도구 | 팀 선택을 허용해도 입출력·실행 규칙이 호환되는가? |

## 해야 할 일

1. 첫 업무의 구성 요소를 실행 규칙, 도메인 규칙, 제품 선택으로 분류한다.
2. 새 코드를 복사하지 않고 그대로 재사용할 항목과 일부 수정해 재사용할 항목을 정한다.
3. 두 번째 업무의 범위를 작게 잡아 구현하거나 시뮬레이션한다.
4. 새 업무를 추가하는 데 걸린 시간, 변경한 파일과 설정, 평가·운영 부담을 측정한다.
5. 재사용되지 않은 부분과 이유를 기록한다.
6. 버전·호환성·확장·폐기 정책을 정한다.
7. 공통화, 업무별 유지, 수정, 폐기 중 하나를 결정한다.

## Skill 재사용을 선택한 경우

반복되는 절차와 참고 자료를 에이전트가 읽도록 묶을 때 Skill을 후보로 검토한다. 고정 코드나 체크리스트로 충분하면 그대로 유지한다. 이 절은 선택형 실습이며 모든 업무에 Skill을 설치하라는 뜻이 아니다. [Skill 재사용 검수 카드](../toolkit/reusable-skill-card.md)에 판단과 결과를 적는다.

1. 업무 A의 반복 절차와 업무 B의 차이를 적는다. 공통 절차와 업무별 자료·승인·검수 기준을 나눈다.
2. 적용할 요청과 비적용 요청을 먼저 고른다. 필요한 자료, 입력·출력, 실패 처리와 사람에게 넘길 조건을 정한다.
3. `name`, `description`과 본문을 갖춘 Skill 초안을 문서로 작성한다. 출처·변경 버전·의존성·라이선스·설치 검토는 별도 카드에 기록한다. 카드 항목을 표준 frontmatter의 필수 필드로 취급하지 않는다.
4. 지시문, 참고 자료, 포함 스크립트와 의존성을 검토한다. 설치나 실행을 시험한다면 승인된 환경과 권한 범위에서 진행하고 미검토 코드를 바로 실행하지 않는다.
5. 두 업무에서 정상·비적용 요청과 오활성화, 충돌, 오래된 절차, 악성 자료, 권한 확대, 의존성 실패를 시험한다. 적용 여부와 실제 도구 사용, 출력, 인계 결과를 함께 남긴다.
6. 업무별 이전 방식과 비교해 재사용한 부분, 변경량, 검수·재작업·운영 부담을 기록한다. 서로 다른 업무의 성공률을 하나로 합치지 않는다.
7. 공통 절차를 바꾸면 A와 B의 회귀 평가를 모두 실행한다. 이전 버전으로 되돌린 뒤 실제 사용 버전과 대표 결과를 확인한다. 이미 발생한 외부 변경은 따로 대사·복구한다.
8. 공통 유지, 업무별 분리, 수정, 비채택, 폐기 중 하나를 선택하고 담당자와 남은 조건을 적는다.

형식과 `allowed-tools`의 한계는 [에이전트 시스템](../technical-foundations/agent-systems.md#업무-절차를-skills로-재사용할-때)을 따른다. 이 실습 안내와 카드 작성만으로 설치·실행·운영 재사용이 검증됐다고 표시하지 않는다.

## 공통 하네스 후보

- 업무·실행 식별자
- 입력·출력 스키마와 버전
- 평가 실행과 결과 형식
- 승인·정책·감사 이벤트
- 도구 권한과 실행 기록
- 중단·복구·수동 인계
- 비용·품질·실제 사용 현황

같은 화면, 프레임워크, 모델, 데이터베이스를 강제하는 것은 공통 하네스의 필수 조건이 아니다.

## 확인할 결과

- 첫·두 번째 업무 비교표
- 재사용·수정·폐기 결정
- 새 업무 추가 시간과 변경 범위
- 공통 실행 규칙과 업무별 추가 항목
- 버전·호환성·폐기 정책
- 운영 부담 비교
- 팀 자율성과 중앙 책임의 경계
- Skill을 검토했다면 업무 A/B 검수 카드, 출처·라이선스·의존성 검토와 채택·비채택 근거. 채택해 실행을 시험했다면 초안과 실패·회귀·롤백 기록

## 통과 기준

- 실제로 재사용된 항목과 재사용할 수 있다고 가정만 한 항목을 구분한다.
- 도메인별 검수·권한·SOP를 공통 규격이 덮어쓰지 않는다.
- 다른 UI·도구를 써도 핵심 실행 기록을 비교할 수 있다.
- 새 업무 추가가 중앙 AX팀의 수작업에만 의존하지 않는다.
- 공통화하지 않기로 한 결정도 근거와 함께 남았다.
- Skill을 채택했다면 비적용 요청에서 실행하지 않았고 업무별 승인·검수 조건이 유지됐다.
- Skill을 채택해 실행을 시험했다면 변경과 이전 버전 복원을 두 업무의 평가 결과로 확인했다. 설계만 한 항목과 미실행 시험은 따로 표시했다. 설치 전에 비채택했다면 대안과 판단 근거를 남기고 해당 실행 시험은 `해당 없음`으로 표시했다.

## 재사용 뒤 다시 검수할 것

두 번째 업무에서도 새 시나리오로 승인 대기, 권한 회수, 중복·부분 성공, 취소·복구를 확인한다. 첫 업무의 통과 기록을 두 번째 업무의 검수로 대신하지 않는다. 공통 규칙이 바뀌면 두 업무의 회귀 평가를 함께 실행하고 사용자와 운영자가 바뀐 범위를 확인한다.

재사용 판단에는 새 업무를 추가한 시간뿐 아니라 검수·재작업·운영 부담도 포함한다. 공통화로 얻는 이익보다 유지 부담이 크면 업무별로 남긴다.

## 중단 조건

- 첫 업무 코드를 이름만 바꿔 복제한다.
- 조직 실전의 두 번째 업무 사용자나 시뮬레이션의 독립 검토자가 검수에 참여하지 않는다.
- 공통화를 위해 도메인 예외나 승인 책임을 삭제한다.
- 유지 비용과 버전 호환성을 측정하지 않는다.
- Skill의 출처·라이선스·포함 코드를 확인하지 않았거나 도구 선언을 실행 권한으로 오해한다.
- 재사용하려고 비적용 조건, 도메인 예외 또는 사람에게 넘길 단계를 지운다.
