# 프로젝트 2. 담당자 승인 워크플로우

## 목표

AI가 업무 변경안을 제안하고, 권한 있는 담당자가 근거와 변경 전후를 확인한 뒤 승인·수정·거절하는 흐름을 만든다. 승인 버튼을 만들기 전에 승인자가 판단할 때 필요한 정보와 기준부터 정한다.

## 추천 업무

- 고객 답변 초안 승인
- 재고·발주 변경 제안
- 캠페인 설정 변경 제안
- 문서 분류와 후속 업무 배정 제안
- 정산 예외의 처리안 제안

이 단계에서는 승인 결과를 모의 실행 기록으로 남긴다. 실제 시스템에 쓰는 시험은 P3의 격리된 테스트 환경에서 진행하고 운영 환경 변경은 P4 실전 조건과 승인을 갖춘 뒤에 진행한다.

## 업무 흐름

```text
업무 입력
→ 제안과 근거 생성
→ 정책·스키마 검사
→ 승인자가 변경 전후·영향 확인
→ 승인·수정·거절
→ 결정과 이유 기록
→ 모의 실행 또는 다음 담당자 인계
```

## 해야 할 일

1. 승인이 필요한 변경의 영향과 승인 권한을 정한다.
2. 승인 화면이나 문서에 원본, 제안, 변경 전후, 근거, 위험을 함께 보여 준다.
3. `승인`, `수정 후 승인`, `거절`, `추가 정보 요청` 기준을 만든다.
4. 승인자 부재, 권한 없는 승인, 오래된 데이터, 중복 요청을 시험한다.
5. 모델 제안과 승인 결과, 수정 이유를 같은 식별자로 기록한다.
6. 승인 대기 시간과 수정 부담을 측정한다.
7. 승인자가 별도 설명 없이도 대표 사례를 처리할 수 있는지 확인한다.

## 승인 대기 중 시험할 상황

승인은 요청 내용과 버전에 묶는다. 승인 뒤 내용·데이터·권한이 달라지면 이전 승인을 그대로 사용하지 않는다. 다음 상황은 모의 실행으로도 시험할 수 있다.

| 상황 | 기대 행동 | 남길 증거 |
|---|---|---|
| 승인 대기 중 화면을 닫고 다시 접속 | 저장한 요청과 승인 상태를 불러오고 접속 자체를 승인으로 처리하지 않음 | 같은 요청 ID와 상태 복원 기록 |
| 승인자가 바뀌거나 권한을 회수 | 실행 직전 권한을 다시 확인하고 권한이 없으면 보류 | 회수 시각, 권한 판정, 보류 이유 |
| 제안·원본 데이터·정책이 변경 | 바뀐 내용을 보여 주고 필요한 승인을 다시 요청 | 승인 대상 버전과 변경 비교 |
| 승인·실행 요청이 중복 도착 | 같은 승인으로 새 실행을 추가하지 않음 | 중복 요청과 최초 결정의 연결 |
| 사용자가 취소하거나 승인 기한이 지남 | 대기 요청을 닫고 이후 실행을 막음 | 취소·만료 상태와 실행 차단 기록 |

대기 시간에는 사람이 검토한 시간과 승인자를 기다린 시간을 구분한다. 자주 보류되는 이유를 모아 제안 품질, 담당자 배정, 권한 절차 중 무엇을 고칠지 결정한다. 이 시험에서 승인 우회가 발생하면 다음 단계로 진행하지 않는다.

## 역할별 수행

- 비개발 실무자: 승인 기준과 예외, 변경 전후의 업무 의미를 정의한다.
- AX 엔지니어: 정책 검사, 승인 상태, 감사 기록을 구현한다.
- 리더·거버넌스: 위임·대체 승인자·중단 권한을 정한다.
- 데이터·보안·운영: 승인 기록, 접근 권한, 보유 범위를 확인한다.

## 확인할 결과

- 책임과 승인표
- 승인 상태 전이와 입력·출력 계약
- 정상·거절·정보 부족 사례
- 변경 전후와 근거를 보여 주는 화면 또는 문서
- 승인·수정·거절 로그
- 승인 대기·수정 부담 측정
- 승인 우회 시험

## 통과 기준

- 승인자는 무엇이 바뀌고 어떤 영향이 있는지 확인할 수 있다.
- 권한 없는 사람이나 만료된 요청은 승인할 수 없다.
- 수정과 거절 이유가 다음 평가에 반영된다.
- 승인 기록만으로 누가 무엇을 허용했는지 재구성할 수 있다.
- 승인 없이 모의 실행도 처리되지 않으며 이 단계에서 실제 시스템을 변경하지 않는다.

## 중단 조건

- 승인자가 근거를 확인하지 않고 결과 전체만 보고 판단한다.
- 승인 상태와 실제 실행 상태가 달라진다.
- 오래된 입력이 최신 제안처럼 표시된다.
- 승인 우회나 권한 오류를 탐지할 수 없다.
