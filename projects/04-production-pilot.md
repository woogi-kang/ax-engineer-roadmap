# 프로젝트 4. 운영 파일럿

## 목표

실제 조직에서는 위험이 낮은 업무 하나를 골라 제한된 사용자만 참여하는 환경에서 운영한다. 공개 시뮬레이션에서는 운영 조건과 장애 대응을 재현하되 실제 현업 정착이나 조직 성과를 주장하지 않는다.

## 진입 조건

- 업무 책임자, 데이터 소유자, 배포·중단 책임자가 정해졌다.
- 기준선과 성공·중단 조건이 있다.
- 평가, 승인, 권한, 로그, 복구, 수동 대체가 샌드박스에서 검증됐다.
- 개인정보·보안·법무 적용 여부를 담당자가 확인했다.
- 실제 사용자와 이중 운영·SOP 계획을 합의했다.

하나라도 빠지면 앞 프로젝트로 돌아간다.

## 파일럿 범위

다음 항목을 숫자나 명확한 조건으로 제한한다.

- 사용자와 조직 단위
- 업무 유형과 제외 사례
- 데이터와 원본 시스템
- 읽기·쓰기 권한
- 일일·주간 실행량
- 모델·도구 비용
- 파일럿 기간
- 자동 실행과 담당자 승인 범위

## 해야 할 일

1. 배포 전 기준선과 대표 실패를 다시 측정한다.
2. 점진적으로 사용자와 실행량을 늘린다.
3. 품질·지연·비용·장애·승인 대기·수정 부담을 관찰한다.
4. 실제 사용자가 대표 업무를 검수하고 예외를 처리한다.
5. 자동 실행 차단, 롤백, 수동 대체 훈련을 한다.
6. 새 SOP를 적용하고 교육·지원 채널을 운영하며 인수인계를 진행한다.
7. 확대·유지·수정·중단 중 하나를 근거로 결정한다.
8. 기존 절차의 유지·종료 상태를 기록한다.

## 확인할 결과

- 파일럿 범위와 승인
- 배포 전 기준선과 평가 결과
- 운영 상태 보고와 SLO
- 사용자 검수·수정·지원 기록
- 장애·중단·복구 훈련
- SOP와 운영 인수인계
- 기존 절차 유지·종료 결정
- 성과·한계·의사결정 기록

## 통과 기준

- 모델 품질과 업무 결과를 따로 설명할 수 있다.
- 실제 사용자가 대표 정상·예외 흐름을 수행했다.
- 장애가 나도 업무를 계속하고 누락·중복 결과를 확인할 수 있다.
- 운영 책임이 구현자 개인에게 남아 있지 않다.
- 확대·유지·수정·중단 결정이 사전에 정한 기준과 실제 결과에 연결된다.

## 공개 시뮬레이션 대안

조직 환경이 없다면 다음을 공개한다.

- 실제 운영 대신 사용한 가정과 모의 역할
- 합성 트래픽과 의도적으로 재현한 장애의 범위
- 사용자 검수 대신 독립 검토자가 확인한 내용
- 실제로 검증하지 못한 현업 사용·보안·법률·조직 조건
- 운영 성과를 주장하지 않는 이유

## 중단 조건

- 심각한 금지 결과나 권한 이상이 발생한다.
- 기준선과 비교할 데이터를 수집할 수 없다.
- 수동 대체가 실제 업무량을 감당하지 못한다.
- 사용자 수정 부담이나 지원 요청이 허용 기준을 넘는다.
- 운영 책임자 없이 파일럿 기간이 연장된다.
