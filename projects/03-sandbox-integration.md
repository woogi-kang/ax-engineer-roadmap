# 프로젝트 3. 샌드박스 통합

## 목표

테스트 환경의 기존 시스템에 통합해 읽기·쓰기, 권한, 중복, 부분 실패, 복구를 검증한다. 실제 고객 데이터나 금전·운영 데이터에는 영향을 주지 않는다.

## 추천 구성

- 테스트 CRM에서 고객 상태 조회·메모 추가
- 테스트 주문 시스템에서 배송 상태 변경
- 샌드박스 협업 도구에서 승인된 메시지 전송
- 합성 데이터베이스에서 작업 생성·상태 변경

## 업무 흐름

```text
승인된 요청
→ 권한·스키마·중복 검사
→ 샌드박스 실행
→ 결과 확인
→ 부분 성공 뒤 누락·중복 확인
→ 완료 또는 담당자 인계
```

## 해야 할 일

1. 테스트와 실제 계정·데이터·시크릿을 분리한다.
2. 조회 도구와 변경 도구를 분리한다.
3. 실행 키와 상태 전이를 정의한다.
4. 타임아웃, 권한 거부, 부분 성공, 중복 요청, 외부 장애를 의도적으로 재현한다.
5. 자동 재시도, 담당자 인계, 즉시 중단을 실패 유형별로 정한다.
6. 이전 상태로 복원하고 수동 절차로 전환하는 과정을 실제로 실행한다.
7. 구현자가 아닌 운영자가 로그를 보고 대표 장애를 처리한다.

## 상태와 권한이 바뀌는 시험

| 상황 | 기대 행동 | 남길 증거 |
|---|---|---|
| 승인 대기 또는 실행 중 프로세스 재시작 | 저장된 상태에서 이어가고 완료된 외부 작업을 반복하지 않음 | 재시작 전후 실행 ID와 외부 작업 ID |
| 외부 작업 성공 뒤 응답 유실 | 원본 시스템에서 결과를 확인한 뒤 재시도 여부 결정 | 조회 결과와 중복 방지 기록 |
| 여러 작업 중 일부만 성공 | 성공·실패·미실행을 나누고 남은 작업의 처리 방식을 결정 | 단계별 상태와 보정 또는 인계 기록 |
| 승인 뒤 서비스 권한 회수 | 실행 직전의 권한으로 판정하고 남은 변경을 차단 | 권한 회수와 차단 시각 |
| 실행 중 취소 요청 | 새 작업을 막고 이미 시작한 작업은 실제 상태를 확인 | 취소 요청, 진행 중 작업, 완료·보정·인계 결과 |

취소할 수 없는 외부 작업은 취소 완료로 표시하지 않는다. 담당자에게 현재 상태와 필요한 조치를 넘긴다. 운영자는 구현자의 도움 없이 이 기록을 읽고 같은 장애를 복구해야 통과한다.

## API가 없는 업무의 화면 조작 실습

공식 API나 MCP 도구로 필요한 동작을 할 수 없다면 [화면 연동 실습 점검표](../toolkit/ui-integration-checklist.md)에 선택 이유와 소유자 허용 범위를 적는다. 기존 테스트 시스템의 합성 자료를 사용한다. 테스트 환경이 없으면 문서로 실패 상황과 판단을 검토하고 실제 연동을 검증했다고 표시하지 않는다.

1. 테스트 계정·조직·대상 ID와 변경 전 상태를 확인한다.
2. 제출할 내용, 수신자, 대상, 허용 동작과 요청 버전을 고정해 승인 기록에 연결한다.
3. 승인 범위 안에서 조작하고 원본 시스템의 저장 결과와 처리 이력을 확인한다.
4. 점검표의 로그인 만료, UI 변경, 잘못된 대상, 악성 지시, 중복 제출, 부분 성공, 재접속을 각각 시험한다.
5. 취소·복구·인계를 수행하고 구현자 외 운영자가 마스킹한 기록으로 결과를 검수한다.

클릭 성공이나 완료 메시지만으로 통과시키지 않는다. 대상이나 결과가 불명확하면 보류하고 CAPTCHA·2FA·서명 등 사람에게 맡길 단계에서 자동 조작을 멈춘다. 이 절차는 추가 실습 지침이며 기존 사례에 화면 조작 코드가 구현됐다는 뜻은 아니다.

## 역할별 수행

- 비개발 실무자: 부분 성공의 업무 의미와 수동 처리 우선순위를 정한다.
- AX 엔지니어: 통합, 상태, 중복 방지, 복구를 구현한다.
- 리더·거버넌스: 실제 운영으로 이동할 위험 허용 기준을 정한다.
- 데이터·보안·운영: 계정·권한·로그·장애 훈련을 검증한다.

## 확인할 결과

- 샌드박스 격리 설명
- API·이벤트·상태 계약
- 역할·서비스 계정 권한표
- 중복 방지와 부분 실패 시험
- 로그·메트릭·트레이스 또는 동등한 실행 기록
- 롤백·수동 대체·누락 및 중복 확인 기록
- 운영 인수인계 확인

## 통과 기준

- 테스트 요청이 실제 환경에 도달할 수 없다.
- 같은 실행 키를 반복해도 외부 부작용이 중복되지 않는다.
- 부분 성공 상태를 숨기지 않고 누락과 중복을 확인할 수 있다.
- 자동 재시도 조건과 중단 조건이 다르다.
- 구현자의 도움 없이 운영자가 대표 장애를 진단·복구했다.

## 중단 조건

- 테스트 계정과 실제 계정을 분리하지 않았다.
- 외부 실행 결과를 확인하지 않고 성공으로 기록한다.
- 롤백이 다른 유효한 변경을 덮어쓴다.
- 로그 없이는 누락·중복을 찾을 수 없다.

## 다음 단계로 가기 전 질문

P3를 통과했고 업무 책임자와 실제 사용자가 범위, SLO, 장애 대응, 기존 절차의 유지·종료 방안에 합의했다면 [P4 운영 파일럿](04-production-pilot.md)을 검토한다. 조직 조건이 없으면 같은 문서의 공개 시뮬레이션 조건을 적용한다. 테스트 실행 근거도 없다면 다음 단계의 실행 검증은 보류하고 설계만 남긴다.
