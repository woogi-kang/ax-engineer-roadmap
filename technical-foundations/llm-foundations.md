# LLM 기초

## 왜 필요한가

LLM은 확률적으로 결과를 생성한다. 입력 형식과 모델 이름만 정해서는 품질·비용·지연을 관리하고 최신성과 출처를 확인할 수 없다. 모델의 특성을 업무의 허용 범위와 평가 조건으로 바꿀 수 있어야 한다.

## 알아야 할 것

- 토큰화와 입력·출력 길이
- 컨텍스트 창과 정보 배치
- 생성 제어와 비결정성
- 구조화 출력과 스키마 검증
- 모델별 기능·지연·비용·데이터 처리 조건
- 프롬프트, 검색, 미세조정의 역할 차이
- 임베딩과 의미 기반 검색
- RAG의 검색·생성 단계와 출처
- 모델 버전 변경과 회귀 위험

## 선택할 조건

### 규칙, 분류, 검색, 생성

- 값이 명확한 조건이면 규칙 기반 처리를 우선한다.
- 정해진 범주로 나누는 일이면 분류를 검토한다.
- 기존 사실을 찾아 보여 주는 일이면 검색 품질을 먼저 본다.
- 새 문장이나 제안이 필요할 때 생성을 사용한다.

한 요청에 모두 넣지 말고 실패 원인을 나눠 볼 수 있게 단계를 분리한다.

### RAG와 원본 조회

정책·매뉴얼처럼 문서 근거가 필요한 질문에는 RAG를 고려할 수 있다. 주문 상태, 재고, 승인 상태처럼 현재 값이 중요한 정보는 원본 시스템에서 먼저 조회한다. 검색 인덱스를 최신 업무 상태를 확인하는 원본으로 사용하지 않는다.

### 더 큰 모델

품질 문제의 원인이 누락된 데이터, 모호한 지시, 잘못된 검색, 불분명한 판정 기준이면 모델 크기를 바꾸기 전에 그 원인을 고친다. 모델 변경은 같은 평가 세트로 비용·지연·품질을 비교한다.

## 직접 해볼 것

1. 실제 또는 공개 사례에서 정상·경계·실패 입력을 모은다.
2. 규칙 기반 방식과 LLM 방식을 비교한다.
3. 검색 결과와 생성 결과를 따로 평가한다.
4. 출처가 없거나 충돌하는 사례의 거절·인계 규칙을 만든다.
5. 모델·프롬프트·컨텍스트 변경 전후를 회귀 평가한다.
6. 토큰, 지연, 비용 한도를 넘는 입력을 시험한다.

## 확인할 결과

- 모델 선택 근거와 대안
- 프롬프트·검색·모델 버전
- 평가 세트와 결과
- 토큰·비용·지연 측정
- 출처·거절·인계 규칙
- 모델 변경 승인과 회귀 기록

## 실패 패턴

- 컨텍스트 창이 크면 모든 문서를 넣어도 된다고 생각한다.
- 검색 결과의 출처·최신성·누락을 숨긴다.
- 좋은 예시 몇 개만 보고 품질을 확정한다.
- 모델 출력이 유창하다는 이유로 사실이 정확하고 업무에도 맞는다고 판단한다.
- 모델 가격만 비교하고 통합·평가·수정 비용을 빼놓는다.

## 함께 합의할 사람

- 업무 책임자: 좋은 결과와 거절 조건
- 데이터 소유자: 원본·복제·최신성
- 보안·개인정보 담당자: 입력·보관·공급자 조건
- 운영 담당자: 비용·지연·장애 한도
