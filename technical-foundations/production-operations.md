# 운영과 관측성

## 왜 필요한가

프로토타입은 성공한 실행을 보여 준다. 운영은 실패한 실행을 발견하고 영향 범위를 확인하며 업무를 계속하게 해야 한다. 모델 품질, 시스템 안정성, 비용, 승인 대기, 사용자 수정 부담을 함께 관찰해야 한다.

## 알아야 할 것

- 로그, 메트릭, 트레이스의 역할
- 실행·업무 식별자와 상관관계
- SLI, SLO, 오류 예산
- 품질·지연·비용 한도
- 경보와 담당자
- 배포, 기능 차단, 롤백
- 재시도, 큐, 부분 성공, 대사
- 장애 대응, 사후 검토, 수동 대체

## 선택할 조건

### 무엇을 기록할까

대화 전문보다 원인 추적에 필요한 구조화 필드를 먼저 정한다.

```text
실행·업무 식별자
사용자·서비스 역할
입력 참조와 데이터 버전
모델·프롬프트·도구 버전
정책 판정과 승인
외부 실행 결과
오류·재시도·중단·복구
비용·지연
```

개인정보·기밀은 최소화하고 보유 기간과 접근 권한을 둔다.

### 언제 자동 재시도할까

일시적이고 부작용이 없거나 중복 방지가 보장될 때만 자동 재시도한다. 금전·메시지·주문 변경처럼 부작용이 있는 작업은 실행 결과를 대사한 뒤 재시도한다.

### 언제 중단할까

금지 행동, 권한 이상, 품질 급락, 비용·반복 한도 초과, 원본 시스템 불일치가 발생하면 자동 범위를 줄이거나 즉시 중단한다. 중단 권한과 사용자 안내를 배포 전에 정한다.

## 직접 해볼 것

1. 한 실행을 서비스 경계 전체에서 추적한다.
2. 품질·비용·지연·오류·승인 대기 지표를 만든다.
3. 외부 API 장애, 모델 오류, 오래된 데이터, 권한 거부를 주입한다.
4. 경보를 받고 자동 실행을 차단한다.
5. 이전 버전 또는 수동 절차로 전환한다.
6. 복구 뒤 누락·중복 결과를 대사한다.
7. 구현자 없이 운영자가 같은 절차를 수행한다.

## 남길 증거

- 관측 필드와 보유 정책
- 대시보드 또는 상태 보고
- SLO와 경보 기준
- 장애 주입·중단·복구 기록
- 수동 대체와 대사 결과
- 사후 검토와 재발 방지 결정
- 운영 인수인계 확인

## 실패 패턴

- 대화 전문을 저장하면 감사와 관측이 끝났다고 생각한다.
- 모델 오류율만 보고 승인 대기와 사용자 수정 부담을 놓친다.
- 경보가 담당자와 복구 절차에 연결되지 않는다.
- 롤백 문서는 있지만 실제로 실행하지 않는다.
- 성공한 외부 작업을 재시도해 중복 결과를 만든다.

## 함께 합의할 사람

- 업무 책임자: 업무 영향과 수동 처리 우선순위
- 개인정보·보안 담당자: 기록·보유·접근
- 시스템 소유자: 장애와 대사 방식
- 리더: SLO, 비용 한도, 중단 권한
