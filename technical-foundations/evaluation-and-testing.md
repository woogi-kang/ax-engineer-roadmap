# 평가와 테스트

## 왜 필요한가

LLM 시스템은 입력, 검색, 모델, 프롬프트, 도구, 정책, 외부 시스템이 함께 결과를 만든다. 좋은 예시 몇 개로는 변경의 영향을 알 수 없다. 평가가 없으면 품질 문제와 업무 문제를 구분할 수 없고 안전하게 버전을 바꿀 수도 없다.

## 알아야 할 것

- 업무 성공 기준과 모델 품질 지표의 차이
- 정상·경계·실패·공격 사례
- 규칙 기반 판정, 담당자 판정, 모델 보조 판정
- 검색, 생성, 도구 선택, 실행 결과의 단계별 평가
- 오프라인 평가와 운영 평가
- 회귀 평가와 변경 승인
- 표본 범위, 누락, 편향, 판정자 일치도
- 비용·지연·안전성 지표

## 선택할 조건

### 자동 판정과 담당자 판정

형식, 필수값, 금지 문자열, 정확한 정답은 규칙으로 판정한다. 의미·톤·업무 적합성은 판정 기준과 대표 사례를 마련해 담당자가 검토한다. 모델의 판정은 보조 수단으로만 사용하고 담당자 판정과의 차이를 점검한다.

### 오프라인과 운영

오프라인 평가는 변경 전 빠른 비교에 적합하다. 운영 평가는 실제 입력 분포, 사용자 수정, 예외, 지연, 비용을 확인한다. 운영 데이터를 평가 세트에 넣을 때 개인정보와 사용 권한을 검토한다.

## 직접 해볼 것

1. 실제 또는 공개 사례에서 대표 입력을 모은다.
2. 정상·경계·실패·공격으로 분류한다.
3. 기대 결과와 판정 기준, 판정자를 적는다.
4. 검색·생성·도구·업무 결과를 따로 측정한다.
5. 프롬프트·모델·도구 변경 전후를 같은 세트로 비교한다.
6. 담당자마다 판정이 다른 사례를 모아 기준을 수정한다.
7. 운영 중 새로운 실패를 발견하면 재현 사례를 추가한다.

## 확인할 결과

- 평가 세트의 출처와 범위
- 판정 기준과 판정자
- 기준선과 변경 후 결과
- 실패 분류와 대표 사례
- 비용·지연·안전성 비교
- 회귀 차단 또는 예외 승인 기록
- 운영 중 발견한 실패를 평가 세트에 추가한 이력

## 실패 패턴

- 평균 점수 하나로 치명적 실패를 가린다.
- 쉬운 정상 사례만 모은다.
- 모델 판정 점수를 절대 기준으로 사용한다.
- 검색 실패와 생성 실패를 한 점수에 섞는다.
- 실제 사용자가 많이 수정해도 모델 평가 점수만 본다.
- 평가 데이터의 개인정보와 공개 권한을 확인하지 않는다.

## 함께 합의할 사람

- 업무 책임자: 성공·거절·담당자 판단 기준
- 사용자: 대표 사례와 수정 부담
- 데이터·보안 담당자: 평가 데이터 사용 범위
- 운영 담당자: 회귀 차단과 긴급 예외
