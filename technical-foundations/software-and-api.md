# 소프트웨어와 API

## 왜 필요한가

AX 시스템은 모델 호출만으로 끝나지 않는다. 사용자, 원본 시스템, 승인, 외부 실행, 결과 기록을 연결해야 한다. 상태·권한·중복·부분 실패를 다루지 못하면 데모가 동작하더라도 실제 업무 운영이 불안정해질 수 있다.

## 알아야 할 것

- HTTP와 REST API의 요청·응답·상태 코드
- 인증과 인가의 차이
- 동기 요청, 비동기 작업, 배치, 이벤트, 웹훅
- 관계형 데이터, 트랜잭션, 상태 전이
- 스키마와 버전 호환성
- 타임아웃, 재시도, 중복 실행 방지와 멱등성(idempotency)
- 환경 설정, 시크릿, 조직 계정
- 단위·통합·종단 간 테스트, CI/CD

## 선택할 조건

### API와 화면 자동화

공식 API가 필요한 기능과 감사를 지원하면 API를 우선한다. 화면 자동화는 필요한 업무를 공식 연결로 처리할 수 없고 업무 가치가 검증될 때 제한된 대안으로 검토한다. 화면 변경, 세션 만료, 개인 계정 의존, 감사 한계를 운영 위험에 포함한다.

브라우저를 쓰는 에이전트도 사이트 접근, 로그인, 실제 변경 승인을 따로 다룬다. OpenAI Agents API의 computer use는 이런 처리를 애플리케이션에 요구하는 구현 예다. [공식 가이드](https://developers.openai.com/api/docs/guides/agents-api/tools/computer-use), [발표 기록](https://developers.openai.com/api/docs/changelog) (추가일 2026-09-29, 확인일 2026-10-26). 클릭이나 제출 메시지 대신 원본 시스템의 상태로 완료를 확인한다.

### 공식 연결을 쓸 수 없는 업무

같은 업무를 공식 API, MCP 연결, 화면 조작으로 처리할 수 있는지 비교하고 선택 근거를 남긴다.

| 경로 | 선택 전에 확인할 것 |
|---|---|
| 공식 API | 필요한 읽기·변경 기능, 인증, 대상 ID, 결과 조회와 중복 방지 |
| MCP 연결 | 제공 도구의 실제 기능, 원본 시스템의 권한, Host·Server 지원과 결과 검증 |
| 화면 조작 | 공식 연결이 부족한 이유, 시스템 소유자의 허용 범위, 테스트 환경과 결과 확인 경로 |
| 사람의 직접 처리 | 자동 조작을 허용하지 않거나 대상·결과를 확실히 확인할 수 없는 경우 |

MCP 연결이 있어도 필요한 업무 기능이나 권한을 제공하는지는 별도 확인한다. 화면 조작은 테스트 계정과 합성 자료로 시작한다. 계정·조직·작업 대상 ID를 확인하고 제출 전 승인 내용과 실제 입력값을 대조한다. API가 없어도 원본 시스템의 상세 화면, 처리 이력, 내보낸 결과 등으로 저장 상태를 확인할 수 있어야 한다.

결과를 확인할 수 없으면 같은 버튼을 다시 누르지 않고 보류한다. 로그인 만료, UI 변경, 악성 화면 지시, 중복 제출, 부분 성공과 재접속은 [화면 연동 실습 점검표](../toolkit/ui-integration-checklist.md)로 시험한다. 제품의 computer use 기능은 구현 선택지이며 화면 자동화의 등장 시점이나 업계 공통 표준을 뜻하지 않는다.

### 동기와 비동기

사용자가 즉시 결과를 기다려야 하고 작업이 짧으면 동기를 고려한다. 외부 시스템이 느리거나 작업이 길고 재시도가 필요하면 비동기 작업과 상태 조회를 고려한다.

### API·SDK 변경

모델 이름이 같아도 API 버전, SDK, 도구 스키마가 달라지면 요청이나 인증 처리에 영향을 줄 수 있다. 예를 들어 Claude API `2026-10-21`은 sampling 인자를 제거했고 해당 SDK 주요 버전은 인증 헤더와 일부 컨텍스트 압축 방식도 바꿨다. 이 예시는 모든 공급자의 공통 규칙이 아니다. [공식 이전 가이드](https://platform.claude.com/docs/en/api/migration-2026-10-21) (API 버전일 2026-10-21, 확인일 2026-10-26).

사용 중인 모델·API·SDK·도구 버전을 고정해 기준선을 남긴다. 변경 뒤에는 정상 응답뿐 아니라 인증 거부, 입력 오류, 타임아웃, 부분 성공도 비교한다. 공급자별 파라미터를 지원 여부 확인 없이 공통 요청에 넣지 않는다.

### 직접 구축과 기존 SaaS

고유한 UI가 필요하다는 이유만으로 새 서비스를 만들지 않는다. 기존 업무 도구 안에서 승인·상태·감사를 충족할 수 있는지 먼저 확인한다.

## 직접 해볼 것

1. 테스트 환경의 두 시스템을 연결한다.
2. 읽기와 쓰기 권한을 분리한다.
3. 입력·출력 스키마와 상태 전이를 정의한다.
4. 타임아웃, 권한 거부, 부분 성공, 중복 요청을 주입한다.
5. 같은 실행 키를 두 번 보내도 외부 작업이 한 번만 적용되게 한다.
6. 다른 개발자가 새 환경에서 같은 동작을 재현할 수 있게 한다.
7. SDK·API 변경 전후에 같은 계약 검사를 실행하고 되돌리는 절차를 확인한다.
8. 화면 자동화를 택했다면 로그인 만료·UI 변경·잘못된 대상 선택·중복 제출을 시험한다.

선택한 연결 방식의 동작과 실패를 검증한다. API·MCP·화면 조작을 모두 구현할 필요는 없다. 사용하지 않는 방식의 전용 항목은 선택 근거와 함께 `해당 없음`으로 남기되 권한·승인·결과 확인·복구 기준은 그대로 적용한다.

## 확인할 결과

- 선택한 연결의 입력·출력·상태 계약(API·MCP·이벤트·화면 조작 등)
- 상태 전이와 오류 분류
- 실행 가능한 코드와 테스트
- 시크릿이 없는 환경 설정 예시
- 배포·롤백 절차
- 재현과 인수인계 기록

## 실패 패턴

- 성공 응답만 처리하고 부분 실패 상태를 저장하지 않는다.
- 자동 재시도가 메시지·결제·주문 변경을 중복 실행한다.
- 사용자 개인 계정과 브라우저 세션에 의존한다.
- 자유 형식 모델 출력을 검증 없이 API 요청으로 보낸다.
- 테스트 환경 없이 실제 시스템에서 첫 통합 시험을 한다.

## 함께 합의할 사람

- 업무 책임자: 상태와 완료의 의미
- 원본 시스템 소유자: 공식 연결과 제한
- 보안 담당자: 인증·인가·시크릿
- 운영 담당자: 재시도·경보·복구
