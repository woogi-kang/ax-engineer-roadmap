# 소프트웨어와 API

## 왜 필요한가

AX 시스템은 모델 호출만으로 끝나지 않는다. 사용자, 원본 시스템, 승인, 외부 실행, 결과 기록을 연결해야 한다. 이때 상태·권한·중복·부분 실패를 다루지 못하면 데모는 동작해도 실제 업무는 손상될 수 있다.

## 알아야 할 것

- HTTP와 REST API의 요청·응답·상태 코드
- 인증과 인가의 차이
- 동기 요청, 비동기 작업, 배치, 이벤트, 웹훅
- 관계형 데이터, 트랜잭션, 상태 전이
- 스키마와 버전 호환성
- 타임아웃, 재시도, 중복 방지, idempotency
- 환경 설정, 시크릿, 조직 계정
- 단위·통합·종단 간 테스트, CI/CD

## 선택할 조건

### API와 화면 자동화

공식 API가 필요한 기능과 감사를 지원하면 API를 우선한다. 화면 자동화는 공식 연결 방식이 없고 업무 가치가 검증될 때 제한된 대안으로 검토한다. 화면 변경, 세션 만료, 개인 계정 의존, 감사 한계를 운영 위험에 포함한다.

### 동기와 비동기

사용자가 즉시 결과를 기다려야 하고 작업이 짧으면 동기를 고려한다. 외부 시스템이 느리거나 작업이 길고 재시도가 필요하면 비동기 작업과 상태 조회를 고려한다.

### 직접 구축과 기존 SaaS

고유한 UI가 필요하다는 이유만으로 새 서비스를 만들지 않는다. 기존 업무 도구 안에서 승인·상태·감사를 충족할 수 있는지 먼저 확인한다.

## 직접 해볼 것

1. 테스트 환경의 두 시스템을 연결한다.
2. 읽기와 쓰기 권한을 분리한다.
3. 입력·출력 스키마와 상태 전이를 정의한다.
4. 타임아웃, 권한 거부, 부분 성공, 중복 요청을 주입한다.
5. 같은 실행 키를 두 번 보내도 외부 작업이 한 번만 적용되게 한다.
6. 다른 개발자가 새 환경에서 재현하게 한다.

## 확인할 결과

- API·이벤트·스키마 계약
- 상태 전이와 오류 분류
- 실행 가능한 코드와 테스트
- 시크릿이 없는 환경 설정 예시
- 배포·롤백 절차
- 재현과 인수인계 기록

## 실패 패턴

- 성공 응답만 처리하고 부분 실패 상태를 저장하지 않는다.
- 자동 재시도가 메시지·결제·주문 변경을 중복 실행한다.
- 사용자 개인 계정과 브라우저 세션에 의존한다.
- 자유 형식 모델 출력을 검증 없이 API 요청으로 보낸다.
- 테스트 환경 없이 실제 시스템에서 첫 통합 시험을 한다.

## 함께 합의할 사람

- 업무 책임자: 상태와 완료의 의미
- 원본 시스템 소유자: 공식 연결과 제한
- 보안 담당자: 인증·인가·시크릿
- 운영 담당자: 재시도·경보·복구
