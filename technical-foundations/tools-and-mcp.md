# 도구 호출과 MCP

## 왜 필요한가

LLM이 문장을 제안하는 것과 시스템에서 조회·전송·수정·삭제를 실행하는 것은 위험 수준이 다르다. 도구 연결은 모델 출력을 실제 업무 영향으로 바꾸므로 스키마, 권한, 승인, 감사, 중복 방지를 함께 설계해야 한다.

## 알아야 할 것

- 함수·도구 정의와 구조화 인자
- 읽기 도구와 쓰기 도구
- 입력 검증, 출력 검증, 정책 판정
- 사용자 권한과 서비스 계정 권한
- 샌드박스와 실제 환경
- 부작용, idempotency, 부분 성공
- MCP의 Host–Client–Server 구조와 기능 협상
- 전송 계층 인증과 업무 수준 승인 차이

## 선택할 조건

### 직접 API와 MCP

한 서비스의 공식 API를 얇게 연결하면 충분할 수 있다. 여러 AI Host에서 같은 도구·리소스를 재사용하고 연결 방식을 표준화할 필요가 있을 때 MCP를 검토한다. MCP 도입 자체를 업무 가치나 보안 통제로 보지 않는다.

### 읽기와 쓰기

첫 실험은 읽기 또는 제안으로 제한한다. 쓰기가 필요하면 별도 도구와 서비스 계정을 사용하고, 스키마 검증·정책·승인·중복 방지를 통과한 요청만 실행한다.

### 모델과 정책 엔진

모델이 자신에게 허용된 권한을 결정하게 하지 않는다. 금지 대상, 한도, 승인 여부는 결정적 코드나 정책에서 판정한다.

## 직접 해볼 것

1. 조회 도구 하나와 변경 도구 하나를 분리해 정의한다.
2. 허용·거절·승인 필요 스키마를 만든다.
3. 잘못된 인자, 권한 없는 사용자, 프롬프트 공격, 중복 요청을 주입한다.
4. 변경 도구를 샌드박스에서만 실행한다.
5. 승인 전후 요청 본문과 결과를 같은 실행 식별자로 기록한다.
6. 도구 연결을 제거해도 수동 업무가 이어지는지 확인한다.

## 남길 증거

- 도구 카탈로그와 소유자
- 입력·출력 스키마
- 읽기·쓰기·승인 권한표
- 샌드박스와 실제 환경 분리
- 정책 거절·승인·실행 로그
- 중복·부분 실패 시험
- 연결 해제와 수동 대체 절차

## 실패 패턴

- 조회만 필요한 Agent에 수정·삭제 기능까지 노출한다.
- 모델이 생성한 자유 형식 문자열을 명령이나 쿼리로 실행한다.
- 사용자의 넓은 권한을 서비스 계정에 그대로 복제한다.
- MCP 인증 지원이 선택 사항일 수 있는데 연결만으로 안전하다고 판단한다.
- 승인 화면은 있지만 승인자가 변경 전후와 근거를 볼 수 없다.

## 함께 합의할 사람

- 원본 시스템 소유자: 공식 API와 부작용
- 업무 승인자: 실행 전 확인할 근거
- 보안 담당자: 인증·인가·서비스 계정
- 운영 담당자: 장애·중복·연결 해제
