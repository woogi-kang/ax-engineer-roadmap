# 에이전트 시스템

## 왜 필요한가

에이전트는 모델이 한 번 답하는 기능이 아니라, 상태를 관찰하고 다음 행동을 정해 도구를 호출하며 결과를 다시 확인하는 시스템이다. 반복 판단이 필요한 문제에는 유용할 수 있지만 비용·지연·예측 불가능성·권한 오남용 위험도 함께 커진다.

## 알아야 할 것

- Agent Loop: 관찰, 판단, 행동, 결과 확인
- 도구 선택과 도구 결과 해석
- 상태, 체크포인트, 중단 조건
- Planner–Executor, ReAct, DAG 등 대표 구조
- 단일 에이전트와 역할을 나눈 다중 에이전트
- 단기 작업 상태와 장기 메모리
- 반복·비용·시간 한도
- 담당자에게 넘길 조건과 승인

## 선택할 조건

Agent Loop를 사용하기 전에 묻는다.

- 단계와 분기가 미리 정해져 있지 않은가?
- 다음 행동이 앞선 결과에 따라 달라지는가?
- 규칙 기반 워크플로우로 풀 때 예외가 지나치게 많은가?
- 각 행동을 독립적으로 검증하고 취소할 수 있는가?
- 반복 횟수·비용·권한을 제한할 수 있는가?

답이 부족하면 고정된 워크플로우, 검색·분류, 초안·승인 방식을 먼저 사용한다.

### 다중 에이전트

역할을 나누면 책임이 분명해지고 평가가 쉬워지는 경우에만 사용한다. 같은 모델 호출을 여러 이름으로 감싸는 구조, 원인 추적이 어려워지는 구조는 피한다.

하위 에이전트마다 입력, 결과 형식, 도구 범위, 시간·비용 한도를 정한다. 상위 에이전트는 누락·충돌·실패 결과를 모아 검수하고 최종 결과를 책임진다. 위임 뒤에도 사람에게 받은 승인 범위를 넓히지 않는다.

### 오래 걸리는 작업과 재개

작업 식별자, 현재 상태, 마지막으로 확인한 외부 결과를 저장한다. 아래는 실습용 상태표다. 선택한 API의 실제 상태값과 연결해서 사용한다.

| 상태 | 저장하거나 확인할 내용 |
|---|---|
| 진행 중 | 실행 단계, 외부 작업 ID, 남은 시간·비용 |
| 추가 입력 필요 | 질문이나 승인 대상, 응답 기한, 재개 조건 |
| 완료 | 원본 시스템의 최종 상태와 검수 결과 |
| 실패 | 성공한 부분, 실패 원인, 재시도·수동 처리 범위 |
| 취소됨 | 실제 중단 확인과 이미 발생한 외부 변경 |

취소 요청은 별도 기록한다. 요청을 접수했다는 응답만으로 작업을 취소됨으로 바꾸지 않는다. MCP Tasks도 취소를 협력적으로 처리하며 작업이 반드시 멈춘다고 보장하지 않는다. [Tasks](https://modelcontextprotocol.io/extensions/tasks/overview) (2026-07-28에 공식 확장으로 이동, 확인일 2026-10-26).

재접속하면 저장한 작업 ID로 상태를 조회한다. 승인 뒤 대상이나 데이터가 바뀌었거나 승인이 만료됐으면 다시 검토한다. 결과가 불명확한 쓰기는 원본과 대사하기 전까지 재실행하지 않는다.

관리형 실행환경도 비교할 수 있다. OpenAI Agents API는 세션·컨텍스트 압축·복구를 관리하는 public beta로 공개됐다. 기능 제공과 별개로 권한·완료 판정·운영 인수 기준은 직접 시험한다. [Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview), [발표 기록](https://developers.openai.com/api/docs/changelog) (발표일 2026-09-10, 확인일 2026-10-26).

### 메모리

업무 원본과 에이전트 메모리를 구분한다. 장기 메모리에는 저장 목적, 출처, 갱신, 정정, 삭제, 접근 권한을 둔다. 모델 요약을 검증 없이 장기 사실로 저장하지 않는다.

### 업무 절차를 Skills로 재사용할 때

반복되는 절차와 참고 자료는 `SKILL.md`와 관련 파일로 묶을 수 있다. 적용할 요청, 적용하지 않을 요청, 필요한 도구, 실패 시 처리, 검수 방법을 함께 적는다. Agent Skills는 YAML frontmatter의 `name`, `description`을 필수로 정하며 `allowed-tools` 필드는 experimental이다. 지원 여부를 확인하고 실제 권한은 실행환경에서 통제한다. [Agent Skills 명세](https://agentskills.io/specification) (확인일 2026-10-26).

Agent Skills의 출시와 표준 공개는 각각 2025년 10월과 12월이며 AAIF 기증 발표는 2026-10-22다. 기능의 등장과 운영 주체의 변경을 구분한다. [공식 발표](https://www.anthropic.com/news/donating-agent-skills-to-the-agentic-ai-foundation) (발행일 2026-10-22, 확인일 2026-10-26). 두 번째 업무에서 재사용하기 전에 출처·변경 버전·의존성을 검토하고 잘못 활성화되거나 절차가 충돌하는 요청도 시험한다.

구체적인 비교와 통과 기준은 [P5의 Skill 재사용 실습](../projects/05-second-workflow-reuse.md#skill-재사용을-선택한-경우)에서 다룬다. [재사용 검수 카드](../toolkit/reusable-skill-card.md)의 버전·설치 검토·라이선스 항목은 로드맵의 별도 기록이며 Agent Skills의 필수 frontmatter 필드가 아니다. 고정 코드나 문서로 충분하면 Skill을 채택하지 않아도 된다.

## 직접 해볼 것

1. 같은 문제를 고정 워크플로우와 Agent Loop로 각각 구현한다.
2. 성공률, 비용, 지연, 재현성, 실패 원인 추적을 비교한다.
3. 최대 단계, 시간, 비용, 도구 범위를 제한한다.
4. 도구 오류, 모순된 결과, 무한 반복, 잘못된 계획을 주입한다.
5. 체크포인트에서 중단·재개하고 담당자에게 넘긴다.
6. 메모리 정정과 삭제가 이후 실행에 반영되는지 시험한다.
7. 승인 대기 중 연결을 끊고 재접속해 작업을 이어 간다. 만료된 승인과 늦게 도착한 도구 결과를 시험한다.
8. 취소 요청 뒤 실제 중단 여부와 외부 변경을 확인한다. 하위 에이전트 실패·결과 충돌·권한 초과도 주입한다.
9. 재사용할 Skill이 있다면 정상 요청과 비적용 요청을 비교하고 승인·검수 조건이 유지되는지 확인한다.

## 확인할 결과

- 에이전트 사용 결정과 더 단순한 대안 비교
- 상태·단계·중단 스키마와 재접속·취소·부분 성공 대사 기록
- 도구 허용 목록과 단계별 권한
- 반복·비용·시간 한도
- 실패 주입과 인계 기록
- 메모리 출처·갱신·삭제 정책

## 실패 패턴

- “자율적”이라는 이유만으로 에이전트를 선택한다.
- 중단 조건 없이 모델이 완료를 스스로 판단한다.
- 여러 에이전트가 같은 데이터를 복제하고 서로 다른 결론을 사실처럼 저장한다.
- 작업 상태와 장기 기억, 업무 원본을 한 저장소에 섞는다.
- 계획 설명을 실제 실행 검증으로 오해한다.

## 함께 합의할 사람

- 업무 책임자: 자율 판단을 허용할 범위
- 보안 담당자: 도구·데이터·실행 권한
- 운영 담당자: 한도·중단·재개·인계
- 데이터 소유자: 메모리의 출처·보유·삭제
