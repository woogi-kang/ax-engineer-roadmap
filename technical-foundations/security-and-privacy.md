# 보안과 개인정보

## 왜 필요한가

LLM 시스템에서는 같은 자연어가 명령으로도, 데이터로도 쓰인다. 신뢰할 수 없는 문서나 메시지가 도구 호출을 유도할 수 있고, 넓은 권한과 과도한 데이터 보관은 작은 오류라도 큰 업무 사고로 바꾼다. 보안·개인정보 보호 기준은 배포 직전에만 검토할 항목이 아니다. 목적을 정할 때부터 운영을 종료할 때까지 함께 설계해야 한다.

## 알아야 할 것

- 데이터 분류, 처리 목적, 최소 수집, 보유·삭제
- 인증, 인가, 최소 권한, 서비스 계정
- 직접·간접 프롬프트 공격
- 민감정보 노출과 안전하지 않은 출력 처리
- 과도한 기능·권한·자율성
- 공급망과 외부 모델·도구
- 샌드박스, 허용 목록, 속도·비용 제한
- 위협 모델, 보안 시험, 사고 대응
- 정보주체 권리, 투명성, 내부 거버넌스

## 선택할 조건

### 데이터를 보낼 수 있는가

업무상 편리함보다 처리 목적, 데이터 종류, 적법 근거, 계약, 저장 위치, 보유·학습 조건, 삭제 방법을 먼저 확인한다. 익명화·가명화로 충분한지, 원본 조회 대신 최소 필드만 보낼 수 있는지 검토한다.

법령은 시행일뿐 아니라 적용 주체, 제품·서비스의 용도, 해당 조항과 예외를 확인한다. 인공지능기본법 시행령 제23조는 고지·표시 방법을 정한다. 제4항은 인공지능사업자의 내부 업무 용도로만 사용하는 경우 등에서 제1~3항의 전부 또는 일부를 적용하지 않을 수 있도록 한다. 이 예외를 개인정보 처리나 다른 법령 의무의 면제로 해석하지 않는다. 현행 법령의 타법개정일만으로 새 의무가 생겼다고 판단하지 않는다. [국가법령정보센터 제23조](https://www.law.go.kr/lsLinkCommonInfo.do?lspttninfSeq=198075) (현행 시행일 2026-08-20, 확인일 2026-10-26).

### 어떤 권한을 줄까

기능을 기준으로 읽기·제안·승인 요청·쓰기·삭제를 분리한다. 모델이 사용할 수 있는 도구 수와 인자 범위를 제한한다. 사용자 권한을 그대로 위임하지 않는다.

### 신원·만료·회수

사람, 에이전트, 서비스 계정을 구분하고 각 자격증명의 소유자와 업무 범위를 적는다. 만료·교체·회수 뒤 실제 호출이 차단되는지 시험한다. 하위 에이전트에 넘기는 권한은 위임자가 받은 범위 안으로 제한한다.

구현 선택지는 공급자마다 다르다. OpenAI는 X.509 workload identity federation을 2026-08-29에 정식 제공했고 프로젝트 API key의 만료와 생성 통제도 추가했다. 키 생성 제한이 기존 키를 자동으로 회수하지는 않는다. [WIF 안내](https://developers.openai.com/api/docs/guides/workload-identity-federation/x509), [키 운영 안내](https://developers.openai.com/api/docs/guides/production-best-practices#api-keys), [발표 기록](https://developers.openai.com/api/docs/changelog) (키 만료 추가일 2026-09-10, 생성 통제 추가일 2026-09-15, 확인일 2026-10-26). 공급자 기능을 모든 환경에서 지원되는 표준으로 가정하지 않는다.

### 정책 서버가 응답하지 않을 때

정책 판단의 시간 초과·오류·연결 실패 때 차단할 작업과 계속 허용할 작업을 미리 정한다. 위험한 쓰기는 정책 확인을 못 했다는 이유로 승인 없이 실행하지 않는다. 경보 담당자, 수동 처리, 복구 뒤 누락·중복 확인을 함께 정한다.

Claude Enterprise inference hooks는 실행 전 정책 판정을 적용하는 공급자 사례다. 정책 서버 장애 시 차단 또는 허용 설정이 있으므로 실제 적용 범위와 장애 동작을 시험해야 한다. [공식 안내](https://platform.claude.com/docs/en/manage-claude/inference-hooks), [발표 기록](https://platform.claude.com/docs/en/release-notes/overview) (beta 종료일 2026-10-20, 확인일 2026-10-26).

### 화면 조작의 접근과 실행 경계

사이트 접근이나 로그인 허용을 발송·수정 승인으로 보지 않는다. 시스템 소유자가 허용한 테스트 환경·계정·업무 범위를 기록하고 실제 변경은 승인한 대상·입력·버전 안에서만 수행한다. 화면이 바뀌거나 다른 조직·대상으로 이동하면 다음 변경을 멈추고 범위를 다시 확인한다.

화면의 문서, 메시지, 팝업에 있는 지시는 업무 데이터로 취급한다. 다른 곳으로 전송하거나 권한을 바꾸라는 문구가 있어도 사용자의 승인으로 해석하지 않는다. CAPTCHA, 2FA, 서명이나 법적으로 사람의 직접 처리가 필요한 단계는 담당자에게 넘긴다. 사람의 처리가 끝나면 최신 대상과 승인 범위를 다시 확인한 뒤 재개한다.

화면 캡처와 실행 기록은 필요한 부분만 남기고 개인정보를 마스킹한다. 비밀번호·토큰·세션 쿠키·인증 코드는 근거 자료에 저장하지 않는다. 로그인 화면이나 민감한 팝업도 기록 범위에서 제외한다. 결과를 확인할 정보가 부족하면 반복 클릭으로 보완하지 않고 보류·인계한다. 구체적인 시험과 증거 항목은 [화면 연동 실습 점검표](../toolkit/ui-integration-checklist.md)를 따른다.

### 프롬프트 공격을 어떻게 볼까

모델에게 “외부 지시를 무시하라”고 쓰는 것만으로 막지 않는다. 신뢰 경계를 표시하고, 외부 콘텐츠를 명령과 분리하며, 도구 인자를 검증한다. 고위험 실행은 코드나 정책으로 정한 규칙과 담당자 승인을 거친다.

## 직접 해볼 것

1. 데이터 흐름과 신뢰 경계를 그린다.
2. 자산, 공격자, 오용, 영향을 위협 모델에 적는다.
3. 외부 문서·메일에 숨긴 지시로 도구 호출을 유도한다.
4. 권한 상승, 민감정보 요청, 금지 대상 실행을 시험한다.
5. 최소 권한 서비스 계정과 샌드박스에서 공격을 재현한다.
6. 로그의 민감정보 마스킹, 보유·삭제, 접근 통제를 확인한다.
7. 사고 시 자동 실행 차단과 보고 절차를 훈련한다.
8. 자격증명 만료·회수, 승인 만료, 위임 범위 초과를 시험한다.
9. 정책 서버가 멈췄을 때 금지된 쓰기가 차단되고 운영자가 복구할 수 있는지 확인한다.

## 확인할 결과

- 데이터 흐름과 처리 목적
- 위협 모델과 위험 관리 책임자
- 역할·에이전트·서비스 계정 권한표와 자격증명 만료·회수 시험
- 정책 서버 장애 시 처리 기준과 훈련 기록
- 공격·오용 평가 세트와 결과
- 샌드박스·허용 목록·한도 설정
- 보유·삭제·정정·접근 절차
- 사고 대응과 개선 기록

## 실패 패턴

- 프롬프트 문구 하나를 보안 경계로 사용한다.
- 모델이 쓰지 않는 기능까지 도구에 노출한다.
- 개인 계정의 넓은 권한을 자동화에 사용한다.
- 모든 입력과 출력을 무기한 저장한다.
- 연결 표준이나 공급자 인증이 업무 승인까지 해결한다고 본다.
- 법률 문구를 일반화해 실제 적용 검토를 생략한다.
